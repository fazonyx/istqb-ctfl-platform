5.1.1. Objectif et contenu d'un plan de test

Un plan de test decrit les objectifs de test, les ressources et les processus pour un projet de test. Un plan de test :

  • Documente les moyens et le calendrier pour atteindre les objectifs de test
  • Aide a s'assurer que les activites de test realisees repondront aux criteres etablis
  • Sert de moyen de communication avec les membres de l'equipe et les autres parties prenantes
  • Demontre que le test respectera la politique de test et la strategie de test existantes (ou explique pourquoi le test s'en ecartera)

La planification des tests guide la reflexion des testeurs et les oblige a anticiper les defis futurs lies aux risques, aux calendriers, aux personnes, aux outils, aux couts, a l'effort, etc. Le processus de preparation d'un plan de test est un moyen utile de reflechir aux efforts necessaires pour atteindre les objectifs de test.

Le contenu typique d'un plan de test comprend :

  • Contexte du test (par ex., portee du test, objectifs de test, base de test)
  • Hypotheses et contraintes du projet de test
  • Parties prenantes (par ex., roles, responsabilites, pertinence pour le test, besoins en recrutement et en formation)
  • Communication (par ex., formes et frequence de la communication, modeles de documentation)
  • Registre des risques (par ex., risques produit, risques projet)
  • Approche de test (par ex., niveaux de test, types de test, techniques de test, livrables de test, criteres d'entree et criteres de sortie, independance du test, metriques a collecter, exigences en donnees de test, exigences en environnement de test, ecarts par rapport a la politique de test et a la strategie de test)
  • Budget et calendrier

Plus de details sur le plan de test et son contenu peuvent etre trouves dans la norme ISO/IEC/IEEE 29119-3.

5.1.2. Contribution du testeur a la planification d'iteration et de release

Dans les SDLC iteratifs, deux types de planification ont generalement lieu : la planification de release et la planification d'iteration.

La planification de release anticipe la livraison d'un produit, definit et redefinit le backlog produit, et peut impliquer le raffinement de user stories plus grandes en un ensemble de user stories plus petites. Elle sert egalement de base a l'approche de test et au plan de test pour toutes les iterations. Les testeurs impliques dans la planification de release participent a la redaction de user stories testables et de criteres d'acceptation (voir section 4.5), participent aux analyses de risques projet et qualite (voir section 5.2), estiment l'effort de test associe aux user stories (voir section 5.1.4), determinent l'approche de test et planifient le test pour la release.

La planification d'iteration anticipe la fin d'une seule iteration et concerne le backlog d'iteration. Les testeurs impliques dans la planification d'iteration participent a l'analyse detaillee des risques des user stories, determinent la testabilite des user stories, decomposent les user stories en taches (en particulier les taches de test), estiment l'effort de test pour toutes les taches de test, et identifient et affinent les aspects fonctionnels et non fonctionnels de l'objet de test.

5.1.3. Criteres d'entree et criteres de sortie

Les criteres d'entree definissent les preconditions pour entreprendre une activite donnee. Si les criteres d'entree ne sont pas remplis, il est probable que l'activite s'averera plus difficile, plus longue, plus couteuse et plus risquee. Les criteres de sortie definissent ce qui doit etre atteint pour declarer une activite terminee. Les criteres d'entree et de sortie doivent etre definis pour chaque niveau de test et differeront en fonction des objectifs de test.

Les criteres d'entree typiques comprennent : la disponibilite des ressources (par ex., personnes, outils, environnements, donnees de test, budget, temps), la disponibilite du testware (par ex., base de test, exigences testables, user stories, cas de test) et le niveau de qualite initial d'un objet de test (par ex., tous les tests de fumee ont reussi).

Les criteres de sortie typiques comprennent : les mesures de rigueur (par ex., niveau de couverture atteint, nombre de defauts non resolus, densite de defauts, nombre de cas de test echoues) et les criteres binaires "oui/non" (par ex., les tests planifies ont ete executes, le test statique a ete effectue, tous les defauts trouves sont rapportes, tous les tests de regression sont automatises).

L'epuisement du temps ou du budget peut egalement etre considere comme un critere de sortie valide. Meme sans que d'autres criteres de sortie soient satisfaits, il peut etre acceptable de terminer le test dans de telles circonstances, si les parties prenantes ont examine et accepte le risque de mettre en production sans tests supplementaires.

En developpement logiciel Agile, les criteres de sortie sont souvent appeles Definition of Done, definissant les metriques objectives de l'equipe pour un element livrable. Les criteres d'entree qu'une user story doit remplir pour demarrer les activites de developpement et/ou de test sont appeles Definition of Ready.

5.1.4. Techniques d'estimation

L'estimation de l'effort de test consiste a predire la quantite de travail lie au test necessaire pour atteindre les objectifs de test d'un projet de test. Il est important de preciser aux parties prenantes que l'estimation est basee sur un certain nombre d'hypotheses et est toujours sujette a une erreur d'estimation. L'estimation pour les petites taches est generalement plus precise que pour les grandes. Par consequent, lors de l'estimation d'une tache importante, elle peut etre decomposee en un ensemble de taches plus petites qui peuvent ensuite etre estimees a leur tour.

Dans ce syllabus, les quatre techniques d'estimation suivantes sont decrites.

Estimation basee sur les ratios. Dans cette technique basee sur les metriques, des chiffres sont collectes a partir de projets precedents au sein de l'organisation, ce qui permet de deriver des ratios "standards" pour des projets similaires. Les ratios des propres projets de l'organisation (par ex., tires de donnees historiques) sont generalement la meilleure source a utiliser dans le processus d'estimation. Ces ratios standards peuvent ensuite etre utilises pour estimer l'effort de test du nouveau projet. Par exemple, si dans le projet precedent le ratio effort de developpement/effort de test etait de 3:2, et que dans le projet actuel l'effort de developpement est estime a 600 jours-personnes, l'effort de test peut etre estime a 400 jours-personnes.

Extrapolation. Dans cette technique basee sur les metriques, des mesures sont effectuees le plus tot possible dans le projet en cours pour collecter les donnees. Ayant suffisamment d'observations, l'effort requis pour le travail restant peut etre approxime en extrapolant ces donnees (generalement en appliquant un modele mathematique). Cette methode est tres adaptee aux SDLC iteratifs. Par exemple, l'equipe peut extrapoler l'effort de test de l'iteration a venir comme la moyenne de l'effort des trois dernieres iterations.

Wideband Delphi. Dans cette technique iterative basee sur les experts, les experts font des estimations basees sur l'experience. Chaque expert, de maniere isolee, estime l'effort. Les resultats sont collectes et si les ecarts de l'estimation d'un expert sont en dehors des limites convenues, les experts discutent de leurs estimations actuelles. Chaque expert est ensuite invite a faire une nouvelle estimation basee sur ce retour, a nouveau de maniere isolee. Ce processus est repete jusqu'a ce qu'un consensus soit atteint. Le Planning Poker est une variante du Wideband Delphi, couramment utilisee dans le developpement logiciel Agile. Dans le Planning Poker, les estimations sont generalement faites a l'aide de cartes avec des nombres representant la taille de l'effort.

Estimation a trois points. Dans cette technique basee sur les experts, trois estimations sont faites par les experts : l'estimation la plus optimiste (a), l'estimation la plus probable (m) et l'estimation la plus pessimiste (b). L'estimation finale (E) est leur moyenne arithmetique ponderee. Dans la version la plus populaire de cette technique, l'estimation est calculee comme E = (a + 4*m + b) / 6. L'avantage de cette technique est qu'elle permet aux experts de calculer l'erreur de mesure : SD = (b – a) / 6. Par exemple, si les estimations (en heures-personnes) sont : a=6, m=9 et b=18, alors l'estimation finale est de 10±2 heures-personnes (c'est-a-dire entre 8 et 12 heures-personnes), car E = (6 + 4*9 + 18) / 6 = 10 et SD = (18 – 6) / 6 = 2.

Exemple concret

Optimiste=1h, Probable=3h, Pessimiste=8h. E = (1 + 4×3 + 8) / 6 = 21/6 = 3,5h par element. Pour 4 taches : 3,5 × 4 = 14h d'effort total estime.

Attention examen

N'oubliez pas de multiplier par le nombre d'elements ! L'erreur classique a l'examen est de donner le resultat pour un seul element au lieu de l'effort total.

5.1.5. Priorisation des cas de test

Une fois les cas de test et les procedures de test specifies et assembles en suites de test, ces suites de test peuvent etre organisees dans un calendrier d'execution des tests qui definit l'ordre dans lequel elles doivent etre executees. Lors de la priorisation des cas de test, differents facteurs peuvent etre pris en compte. Les strategies de priorisation des cas de test les plus couramment utilisees sont les suivantes :

  • Priorisation basee sur le risque, ou l'ordre d'execution des tests est base sur les resultats de l'analyse des risques (voir section 5.2.3). Les cas de test couvrant les risques les plus importants sont executes en premier.
  • Priorisation basee sur la couverture, ou l'ordre d'execution des tests est base sur la couverture (par ex., couverture des instructions). Les cas de test atteignant la couverture la plus elevee sont executes en premier. Dans une autre variante, appelee priorisation par couverture additionnelle, le cas de test atteignant la couverture la plus elevee est execute en premier ; chaque cas de test suivant est celui qui atteint la couverture additionnelle la plus elevee.
  • Priorisation basee sur les exigences, ou l'ordre d'execution des tests est base sur les priorites des exigences retracees jusqu'aux cas de test correspondants. Les priorites des exigences sont definies par les parties prenantes. Les cas de test lies aux exigences les plus importantes sont executes en premier.

Idealement, les cas de test seraient ordonnes pour etre executes en fonction de leurs niveaux de priorite, en utilisant, par exemple, l'une des strategies de priorisation mentionnees ci-dessus. Cependant, cette pratique peut ne pas fonctionner si les cas de test ou les fonctionnalites testees ont des dependances. Si un cas de test de priorite superieure depend d'un cas de test de priorite inferieure, le cas de test de priorite inferieure doit etre execute en premier.

L'ordre d'execution des tests doit egalement tenir compte de la disponibilite des ressources. Par exemple, les outils de test, les environnements de test ou les personnes necessaires qui peuvent n'etre disponibles que pendant une fenetre de temps specifique.

Exemple concret — priorisation par couverture additionnelle

TC1 couvre Req1, Req3, Req4, Req7 (4 exigences) → execute en 1er. TC3 couvre Req5, Req6 (2 exigences nouvelles) → execute en 2e. TC4 couvre Req2 (1 exigence nouvelle) → execute en 3e. TC2 ne couvre aucune exigence supplementaire → execute en dernier.

5.1.6. Pyramide de test

La pyramide de test est un modele montrant que differents tests peuvent avoir differentes granularites. Le modele de la pyramide de test aide l'equipe dans l'automatisation des tests et dans l'allocation de l'effort de test en montrant que differents objectifs de test sont supportes par differents niveaux d'automatisation des tests. Les couches de la pyramide representent des groupes de tests. Plus la couche est elevee, plus la granularite du test est faible, plus l'isolation du test est faible (c'est-a-dire le degre de dependance vis-a-vis d'autres elements du systeme) et plus le temps d'execution du test est eleve. Les tests de la couche inferieure sont petits, isoles, rapides et verifient une petite partie de la fonctionnalite, donc generalement un grand nombre d'entre eux est necessaire pour atteindre une couverture raisonnable. La couche superieure represente des tests complexes, de haut niveau, de bout en bout. Ces tests de haut niveau sont generalement plus lents que les tests des couches inferieures, et ils verifient typiquement une grande partie de la fonctionnalite, donc generalement seuls quelques-uns sont necessaires pour atteindre un niveau de couverture raisonnable.

Le nombre et le nommage des couches peuvent differer. Par exemple, le modele original de la pyramide de test (Cohn 2009) definit trois couches : "tests unitaires", "tests de service" et "tests UI". Un autre modele populaire definit les tests unitaires (composants), les tests d'integration (integration de composants) et les tests de bout en bout. D'autres niveaux de test (voir section 2.2.1) peuvent egalement etre utilises.

5.1.7. Quadrants de test

Les quadrants de test, definis par Brian Marick (Marick 2003, Crispin 2008), regroupent les niveaux de test avec les types de test, activites, techniques de test et produits d'activite appropries dans le developpement logiciel Agile. Le modele aide la gestion de test a les visualiser pour s'assurer que tous les types de test et niveaux de test appropries sont inclus dans le SDLC et a comprendre que certains types de test sont plus pertinents pour certains niveaux de test que d'autres. Ce modele fournit egalement un moyen de differencier et de decrire les types de test a toutes les parties prenantes, y compris les developpeurs, les testeurs et les representants metier.

Dans ce modele, les tests peuvent etre orientes metier ou orientes technologie. Les tests peuvent egalement soutenir l'equipe (c'est-a-dire guider le developpement) ou critiquer le produit (c'est-a-dire mesurer son comportement par rapport aux attentes). La combinaison de ces deux points de vue determine les quatre quadrants :

  • Quadrant Q1 (oriente technologie, soutien a l'equipe). Ce quadrant contient les tests de composants et les tests d'integration de composants. Ces tests doivent etre automatises et inclus dans le processus de CI.
  • Quadrant Q2 (oriente metier, soutien a l'equipe). Ce quadrant contient les tests fonctionnels, les exemples, les tests de user stories, les prototypes d'experience utilisateur, les tests d'API et les simulations. Ces tests verifient les criteres d'acceptation et peuvent etre manuels ou automatises.
  • Quadrant Q3 (oriente metier, critique du produit). Ce quadrant contient les tests exploratoires, les tests d'utilisabilite, les tests d'acceptation utilisateur. Ces tests sont orientes utilisateur et souvent manuels.
  • Quadrant Q4 (oriente technologie, critique du produit). Ce quadrant contient les tests de fumee et les tests non fonctionnels (sauf les tests d'utilisabilite). Ces tests sont souvent automatises.

5.2. Gestion des risques

Objectifs d'apprentissage :

FL-5.2.2 (K2) Distinguer les risques projet des risques produit
FL-5.2.3 (K2) Expliquer comment l'analyse des risques produit peut influencer la rigueur et la portee du test
FL-5.2.4 (K2) Expliquer quelles mesures peuvent etre prises en reponse aux risques produit analyses

Les organisations font face a de nombreux facteurs internes et externes qui rendent incertain si et quand elles atteindront leurs objectifs (ISO 31000). La gestion des risques permet aux organisations d'augmenter la probabilite d'atteindre les objectifs, d'ameliorer la qualite de leurs produits et d'accroitre la confiance des parties prenantes.

Les principales activites de gestion des risques sont :

  • L'analyse des risques (comprenant l'identification des risques et l'evaluation des risques ; voir section 5.2.3)
  • Le controle des risques (comprenant l'attenuation des risques et la surveillance des risques ; voir section 5.2.4)

L'approche de test, dans laquelle les activites de test sont selectionnees, priorisees et gerees sur la base de l'analyse et du controle des risques, est appelee test base sur les risques.

5.2.1. Definition du risque et attributs du risque

Un risque est un evenement potentiel, un danger, une menace ou une situation dont la survenue provoque un effet nefaste. Un risque peut etre caracterise par deux facteurs :

  • Vraisemblance du risque – la probabilite de survenue du risque (superieure a zero et inferieure a un)
  • Impact du risque (prejudice) – les consequences de cette survenue

Ces deux facteurs expriment le niveau de risque, qui est une mesure du risque. Plus le niveau de risque est eleve, plus son traitement est important.

Attention examen

Risque produit = qualite du logiciel (mauvaise architecture, performance, securite). Risque projet = gestion du projet (retard, budget, turnover, competences). Ne confondez pas les deux categories !

5.2.2. Risques projet et risques produit

Dans le test logiciel, on est generalement concerne par deux types de risques : les risques projet et les risques produit.

Les risques projet sont lies a la gestion et au controle du projet. Les risques projet comprennent :

  • Problemes organisationnels (par ex., retards dans la livraison des produits d'activite, estimations inexactes, reductions de couts)
  • Problemes de personnel (par ex., competences insuffisantes, conflits, problemes de communication, manque de personnel)
  • Problemes techniques (par ex., derive du perimetre, support d'outils insuffisant)
  • Problemes de fournisseur (par ex., defaillance de livraison d'un tiers, faillite de l'entreprise de support)

Les risques projet, lorsqu'ils surviennent, peuvent avoir un impact sur le calendrier, le budget ou le perimetre du projet, ce qui affecte la capacite du projet a atteindre ses objectifs.

Les risques produit sont lies aux caracteristiques de qualite du produit (par ex., decrites dans le modele de qualite ISO 25010). Des exemples de risques produit incluent : fonctionnalite manquante ou erronee, calculs incorrects, erreurs d'execution, architecture mediocre, algorithmes inefficaces, temps de reponse inadequat, experience utilisateur mediocre, vulnerabilites de securite. Les risques produit, lorsqu'ils surviennent, peuvent entrainer diverses consequences negatives, notamment :

  • Insatisfaction des utilisateurs
  • Perte de revenus, de confiance, de reputation
  • Dommages a des tiers
  • Couts de maintenance eleves, surcharge du service d'assistance
  • Sanctions penales
  • Dans les cas extremes, dommages physiques, blessures voire deces

5.2.3. Analyse des risques produit

Du point de vue du test, l'objectif de l'analyse des risques produit est de fournir une prise de conscience du risque produit pour concentrer l'effort de test de maniere a minimiser le niveau residuel de risque produit. Idealement, l'analyse des risques produit commence tot dans le SDLC.

L'analyse des risques produit consiste en l'identification des risques et l'evaluation des risques. L'identification des risques consiste a generer une liste exhaustive de risques. Les parties prenantes peuvent identifier les risques en utilisant diverses techniques et outils, par ex., brainstorming, ateliers, entretiens ou diagrammes de cause a effet. L'evaluation des risques implique : la categorisation des risques identifies, la determination de leur vraisemblance, impact et niveau de risque, la priorisation et la proposition de moyens pour les traiter. La categorisation aide a attribuer les actions d'attenuation, car generalement les risques appartenant a la meme categorie peuvent etre attenuer en utilisant une approche similaire.

L'evaluation des risques peut utiliser une approche quantitative ou qualitative, ou un melange des deux. Dans l'approche quantitative, le niveau de risque est calcule comme la multiplication de la vraisemblance du risque et de l'impact du risque. Dans l'approche qualitative, le niveau de risque peut etre determine a l'aide d'une matrice de risque.

L'analyse des risques produit peut influencer la rigueur et la portee du test. Ses resultats sont utilises pour :

  • Determiner la portee du test a realiser
  • Determiner les niveaux de test particuliers et proposer les types de test a effectuer
  • Determiner les techniques de test a employer et la couverture a atteindre
  • Estimer l'effort de test requis pour chaque tache
  • Prioriser le test pour tenter de trouver les defauts critiques le plus tot possible
  • Determiner si des activites supplementaires au test pourraient etre employees pour reduire le risque

5.2.4. Controle des risques produit

Le controle des risques produit comprend toutes les mesures prises en reponse aux risques produit identifies et evalues. Le controle des risques produit consiste en l'attenuation des risques et la surveillance des risques. L'attenuation des risques implique la mise en oeuvre des actions proposees lors de l'evaluation des risques pour reduire le niveau de risque. L'objectif de la surveillance des risques est de s'assurer que les actions d'attenuation sont efficaces, d'obtenir des informations supplementaires pour ameliorer l'evaluation des risques et d'identifier les risques emergents.

En ce qui concerne le controle des risques produit, une fois qu'un risque a ete analyse, plusieurs options de reponse au risque sont possibles, par ex., attenuation du risque par le test, acceptation du risque, transfert du risque ou plan de contingence (Veenendaal 2012). Les actions qui peuvent etre prises pour attenuer les risques produit par le test sont les suivantes :

  • Selectionner les testeurs ayant le bon niveau d'experience et de competences, adapte a un type de risque donne
  • Appliquer un niveau d'independance du test approprie
  • Effectuer des revues et des analyses statiques
  • Appliquer les techniques de test et les niveaux de couverture appropries
  • Appliquer les types de test appropries traitant les caracteristiques de qualite affectees
  • Effectuer des tests dynamiques, y compris des tests de regression

5.3. Suivi des tests, controle des tests et completion des tests

Objectifs d'apprentissage :
FL-5.3.1 (K1) Se rappeler les metriques utilisees pour le test
FL-5.3.2 (K2) Resumer les objectifs, le contenu et les audiences des rapports de test
FL-5.3.3 (K2) Illustrer comment communiquer le statut du test

Le suivi des tests concerne la collecte d'informations sur le test. Ces informations sont utilisees pour evaluer l'avancement des tests et pour mesurer si les criteres de sortie ou les taches de test associees aux criteres de sortie sont satisfaits, comme atteindre les objectifs de couverture des risques produit, des exigences ou des criteres d'acceptation.

Le controle des tests utilise les informations du suivi des tests pour fournir, sous forme de directives de controle, des orientations et les actions correctives necessaires pour obtenir le test le plus efficace et efficient. Des exemples de directives de controle incluent :

  • Re-prioriser les tests lorsqu'un risque identifie devient un probleme
  • Reevaluer si un element de test repond aux criteres d'entree ou de sortie suite a une retouche
  • Ajuster le calendrier de test pour faire face a un retard dans la livraison de l'environnement de test
  • Ajouter de nouvelles ressources quand et ou elles sont necessaires

La completion des tests collecte les donnees des activites de test terminees pour consolider l'experience, le testware et toute autre information pertinente. Les activites de completion des tests se produisent aux jalons du projet, comme lorsqu'un niveau de test est termine, qu'une iteration agile est achevee, qu'un projet de test est termine (ou annule), qu'un systeme logiciel est livre ou qu'une version de maintenance est terminee.

5.3.1. Metriques utilisees dans le test

Les metriques de test sont collectees pour montrer l'avancement par rapport au calendrier et au budget de test prevus, la qualite actuelle de l'objet de test et l'efficacite des activites de test par rapport aux objectifs de test ou a un objectif d'iteration. Le suivi des tests collecte une variete de metriques pour supporter le controle et la completion des tests.

Les metriques de test courantes comprennent :

  • Metriques d'avancement du projet (par ex., achevement des taches, utilisation des ressources, effort de test)
  • Metriques d'avancement du test (par ex., avancement de l'implementation des cas de test, avancement de la preparation de l'environnement de test, nombre de cas de test executes/non executes, reussis/echoues, temps d'execution des tests)
  • Metriques de qualite du produit (par ex., disponibilite, temps de reponse, temps moyen avant defaillance)
  • Metriques de defauts (par ex., nombre et priorites des defauts trouves/corriges, densite de defauts, pourcentage de detection des defauts)
  • Metriques de risque (par ex., niveau de risque residuel)
  • Metriques de couverture (par ex., couverture des exigences, couverture du code)
  • Metriques de cout (par ex., cout du test, cout organisationnel de la qualite)

5.3.2. Objectif, contenu et audience des rapports de test

Le reporting de test resume et communique les informations de test pendant et apres le test. Les rapports d'avancement de test supportent le controle continu des tests et doivent fournir suffisamment d'informations pour apporter des modifications au calendrier de test, aux ressources ou au plan de test, lorsque de tels changements sont necessaires en raison d'ecarts par rapport au plan ou de circonstances modifiees. Les rapports de completion de test resument une activite de test specifique (par ex., niveau de test, cycle de test, iteration) et peuvent fournir des informations pour les tests ulterieurs.

Pendant le suivi et le controle des tests, l'equipe de test genere des rapports d'avancement de test pour les parties prenantes afin de les tenir informees. Les rapports d'avancement de test sont generalement generes de maniere reguliere (par ex., quotidiennement, hebdomadairement, etc.) et comprennent :

  • Periode de test
  • Avancement du test (par ex., en avance ou en retard sur le calendrier), y compris tout ecart notable
  • Obstacles au test et leurs solutions de contournement
  • Metriques de test (voir section 5.3.1 pour des exemples)
  • Risques nouveaux et modifies pendant la periode de test
  • Tests planifies pour la prochaine periode

Un rapport de completion de test est prepare pendant la completion des tests, lorsqu'un projet, un niveau de test ou un type de test est termine et que, idealement, ses criteres de sortie ont ete atteints. Ce rapport utilise les rapports d'avancement de test et d'autres donnees. Les rapports de completion de test typiques comprennent :

  • Resume du test
  • Evaluation du test et de la qualite du produit basee sur le plan de test original (c'est-a-dire les objectifs de test et les criteres de sortie)
  • Ecarts par rapport au plan de test (par ex., differences par rapport au calendrier, a la duree et a l'effort de test prevus).
  • Obstacles au test et solutions de contournement
  • Metriques de test basees sur les rapports d'avancement de test
  • Risques non attenuer, defauts non corriges
  • Lecons apprises pertinentes pour le test

Differentes audiences necessitent differentes informations dans les rapports et influencent le degre de formalite et la frequence du reporting de test. Le reporting d'avancement de test envers les autres membres de la meme equipe est souvent frequent et informel, tandis que le reporting de completion de test suit un modele defini et n'a lieu qu'une seule fois.

La norme ISO/IEC/IEEE 29119-3 comprend des modeles et des exemples de rapports d'avancement de test (appeles rapports de statut de test) et de rapports de completion de test.

5.3.3. Communiquer le statut du test

Le meilleur moyen de communiquer le statut du test varie, en fonction des preoccupations de la gestion de test, des strategies de test organisationnelles, des normes reglementaires ou, dans le cas des equipes auto-organisees (voir section 1.5.2), de l'equipe elle-meme. Les options comprennent :

  • Communication verbale avec les membres de l'equipe et les autres parties prenantes
  • Tableaux de bord (par ex., tableaux de bord CI/CD, tableaux de taches et diagrammes de burn-down)
  • Canaux de communication electroniques (par ex., email, chat)
  • Documentation en ligne
  • Rapports de test formels (voir section 5.3.2)

Une ou plusieurs de ces options peuvent etre utilisees. Une communication plus formelle peut etre plus appropriee pour les equipes distribuees ou la communication directe en face a face n'est pas toujours possible en raison de la distance geographique ou des decalages horaires. Typiquement, differentes parties prenantes sont interessees par differents types d'informations, donc la communication doit etre adaptee en consequence.

5.4. Gestion de configuration

Objectifs d'apprentissage :
FL-5.4.1 (K2) Resumer comment la gestion de configuration supporte le test

Dans le test, la gestion de configuration (CM) fournit une discipline pour identifier, controler et suivre les produits d'activite tels que les plans de test, les strategies de test, les conditions de test, les cas de test, les scripts de test, les resultats de test, les journaux de test et les rapports de test en tant qu'elements de configuration.

Pour un element de configuration complexe (par ex., un environnement de test), la CM enregistre les elements qui le composent, leurs relations et leurs versions. Si l'element de configuration est approuve pour le test, il devient une ligne de base et ne peut etre modifie que par un processus formel de controle des changements.

La gestion de configuration conserve un enregistrement des elements de configuration modifies lorsqu'une nouvelle ligne de base est creee. Il est possible de revenir a une ligne de base precedente pour reproduire des resultats de test anterieurs.

Pour supporter correctement le test, la CM assure ce qui suit :

  • Tous les elements de configuration, y compris les elements de test (parties individuelles de l'objet de test), sont identifies de maniere unique, controles en version, suivis pour les changements et relies a d'autres elements de configuration afin que la tracabilite puisse etre maintenue tout au long du processus de test
  • Toute la documentation identifiee et les elements logiciels sont references sans ambiguite dans le testware

L'integration continue, la livraison continue, le deploiement continu et les tests associes sont typiquement implementes dans le cadre d'un pipeline DevOps automatise (voir section 2.1.4), dans lequel la CM automatisee est normalement incluse.

Exemple concret

Un utilisateur signale un bug en production. Grace a la gestion de configuration, l'equipe retrouve la version exacte du logiciel deployee, reconstitue l'environnement de test identique et reproduit le probleme pour le corriger.

5.5. Gestion des defauts

Objectifs d'apprentissage :
FL-5.5.1 (K3) Preparer un rapport de defaut

Puisque l'un des principaux objectifs du test est de trouver des defauts, un processus de gestion des defauts etabli est essentiel. Bien que nous fassions reference aux "defauts" ici, les anomalies rapportees peuvent s'averer etre de vrais defauts ou autre chose (par ex., resultat faux positif, demande de changement) - cela est resolu au cours du processus de traitement des rapports de defaut. Les anomalies peuvent etre rapportees pendant toute phase du SDLC et la forme depend du SDLC. Au minimum, le processus de gestion des defauts comprend un workflow pour le traitement des defauts ou anomalies individuels, de leur decouverte a leur cloture, et des regles pour leur classification. Le workflow comprend typiquement des activites pour enregistrer les anomalies rapportees, les analyser et les classer, decider d'une reponse appropriee comme corriger ou laisser en l'etat, et enfin cloturer le rapport de defaut. Le processus doit etre suivi par toutes les parties prenantes impliquees. Il est conseille de traiter les defauts du test statique (en particulier l'analyse statique) de maniere similaire.

Les rapports de defaut typiques ont les objectifs suivants :

  • Fournir aux responsables du traitement et de la resolution des defauts rapportes suffisamment d'informations pour resoudre le probleme
  • Fournir un moyen de suivi de la qualite du produit d'activite
  • Fournir des idees pour l'amelioration du processus de developpement et de test

Un rapport de defaut enregistre pendant le test dynamique comprend typiquement :

  • Identifiant unique
  • Titre avec un bref resume de l'anomalie rapportee
  • Date a laquelle l'anomalie a ete observee, organisation emettrice et auteur, y compris leur role
  • Identification de l'objet de test et de l'environnement de test
  • Contexte du defaut (par ex., cas de test en cours d'execution, activite de test effectuee, phase du SDLC et autres informations pertinentes telles que la technique de test, la checklist ou les donnees de test utilisees)
  • Description de la defaillance pour permettre la reproduction et la resolution, y compris les etapes de test qui ont detecte l'anomalie, et tout journal de test, dump de base de donnees, capture d'ecran ou enregistrement pertinent
  • Resultats attendus et resultats reels
  • Severite du defaut (degre d'impact) sur les interets des parties prenantes ou les exigences
  • Priorite de correction
  • Statut du defaut (par ex., ouvert, differe, doublon, en attente de correction, en attente de test de confirmation, reouvert, ferme, rejete)
  • References (par ex., vers le cas de test)

Certaines de ces donnees peuvent etre automatiquement incluses lors de l'utilisation d'outils de gestion des defauts (par ex., identifiant, date, auteur et statut initial). Des modeles de documents pour un rapport de defaut et des exemples de rapports de defaut peuvent etre trouves dans la norme ISO/IEC/IEEE 29119-3, qui fait reference aux rapports de defaut sous le nom de rapports d'incident.

Attention examen

Le rapport de defaut contient les etapes de reproduction, le resultat attendu vs le resultat reel, la severite et la priorite. Ce n'est PAS un rapport de test (qui resume l'avancement ou la completion des tests).

Plan de test : contenu

  • Contexte du test (portee, objectifs, contraintes)
  • Approche de test (niveaux, types, techniques, criteres, metriques)
  • Communication (qui recoit quels rapports, frequence)
  • Registre des risques

Techniques d'estimation

TechniqueDescription
Estimation basee sur les ratiosUtilise un ratio standard (ex: 1 jour de dev = 0.5 jour de test)
Estimation a 3 pointsFormule : E = (a + 4m + b) / 6 (a=optimiste, m=probable, b=pessimiste)
Planning poker (consensus)Chaque membre estime independamment, puis discussion jusqu'au consensus
E = (optimiste + 4 x plus probable + pessimiste) / 6
Comment calculer l'estimation 3 points
  1. Identifier les 3 valeurs : a (optimiste), m (plus probable), b (pessimiste)
  2. Appliquer la formule : E = (a + 4×m + b) / 6
  3. Multiplier par le nombre d'elements (cas de test, taches, etc.)
Exemple : Meilleur cas = 1h, probable = 3h, pire = 8h.
E = (1 + 4×3 + 8) / 6 = (1 + 12 + 8) / 6 = 21 / 6 = 3.5h par cas de test.
Pour 4 cas de test : 3.5 × 4 = 14 heures.
Piege : N'oublie pas de multiplier par le nombre d'elements ! L'erreur classique est de donner 3.5h (un seul cas) au lieu de 14h (les 4).

Priorisation des cas de test

  • Basee sur le risque : tester d'abord les cas a haut risque
  • Couverture additionnelle : choisir les cas qui augmentent le plus la couverture
  • Basee sur les exigences : prioriser selon l'importance des exigences

Pyramide de test

  • Base (beaucoup) : Tests unitaires / composants (rapides, peu couteux, automatises)
  • Milieu (moyen) : Tests d'integration (API, services)
  • Sommet (peu) : Tests UI / systeme / end-to-end (lents, couteux)

Plus on monte dans la pyramide, moins il y a de tests mais plus ils sont couteux et lents.

Gestion des risques

Risque = Probabilite x Impact
Comment calculer le risque
  1. Formule : Niveau de risque = Probabilite × Impact
  2. Si on te donne le niveau et la probabilite → Impact = Niveau / Probabilite
  3. Si on te donne le niveau et l'impact → Probabilite = Niveau / Impact
Exemple : Niveau = 1000$, Probabilite = 50% (= 0.5).
Impact = 1000 / 0.5 = 2000$.
Risque produit (qualite)Risque projet (gestion)

L'analyse de risque produit guide la priorisation des tests : plus le risque est eleve, plus le test doit etre intensif.

Metriques de test

  • Couverture : % d'exigences/code couvert par les tests
  • Defauts : nombre trouves, corriges, en attente, densite, taux de detection
  • Execution : % de tests passes, echoues, bloques, non executes
  • Effort : temps reel vs planifie
