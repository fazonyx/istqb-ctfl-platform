3.1. Bases du test statique

Objectifs d'apprentissage :
FL-3.1.1 (K1) Reconnaitre les types de produits d'activite pouvant etre examines par le test statique
FL-3.1.2 (K2) Expliquer la valeur du test statique
FL-3.1.3 (K2) Comparer et opposer le test statique et le test dynamique

Contrairement au test dynamique, le test statique ne necessite pas l'execution du logiciel sous test. Le code, les specifications de processus, les specifications d'architecture systeme ou d'autres produits d'activite sont evalues par un examen manuel (par exemple, les revues) ou a l'aide d'un outil (par exemple, l'analyse statique). Les objectifs du test incluent l'amelioration de la qualite, la detection des defauts et l'evaluation de caracteristiques telles que la lisibilite, la completude, la correction, la testabilite et la coherence. Le test statique peut etre applique a la fois pour la verification et la validation.

Les testeurs, les representants metier (Product Owner, analyste metier, etc.) et les developpeurs travaillent ensemble lors de sessions de cartographie d'exemples, d'ecriture collaborative de user stories et de raffinement du backlog pour s'assurer que les user stories et les produits d'activite associes repondent aux criteres definis, par exemple la Definition of Ready (voir section 5.1.3). Les techniques de revue peuvent etre appliquees pour s'assurer que les user stories sont completes, comprehensibles et incluent des criteres d'acceptation testables. En posant les bonnes questions, les testeurs explorent, remettent en question et contribuent a ameliorer les user stories proposees.

L'analyse statique peut identifier des problemes avant le test dynamique tout en necessitant souvent moins d'effort, puisqu'aucun cas de test n'est requis et que des outils (voir chapitre 6) sont generalement utilises. L'analyse statique est souvent integree dans les frameworks d'integration continue (voir section 2.1.4). Bien qu'elle soit largement utilisee pour detecter des defauts de code specifiques, l'analyse statique est egalement utilisee pour evaluer la maintenabilite et la securite. Les correcteurs orthographiques et les outils de lisibilite sont d'autres exemples d'outils d'analyse statique.

3.1.1. Produits d'activite examinables par le test statique

Presque tout produit d'activite peut etre examine a l'aide du test statique. Les exemples incluent les documents de specification des exigences, le code source, les plans de test, les cas de test, les elements du backlog produit, les chartes de test, la documentation projet, les contrats et les modeles.

Tout produit d'activite pouvant etre lu et compris peut faire l'objet d'une revue. Cependant, pour l'analyse statique, les produits d'activite doivent avoir une structure permettant leur verification (par exemple, des modeles, du code ou du texte avec une syntaxe formelle).

Les produits d'activite qui ne conviennent pas au test statique sont ceux qui sont difficiles a interpreter par des humains et qui ne devraient pas etre analyses par des outils (par exemple, du code executable tiers pour des raisons legales).

3.1.2. Valeur du test statique

Le test statique peut detecter des defauts dans les phases les plus precoces du SDLC, respectant ainsi le principe du test precoce (voir section 1.3). Il peut egalement identifier des defauts qui ne peuvent pas etre detectes par le test dynamique (par exemple, du code inatteignable, des patterns de conception non implementes comme souhaite, des defauts dans des produits d'activite non executables).

Le test statique offre la capacite d'evaluer la qualite des produits d'activite et de renforcer la confiance en ceux-ci. En verifiant les exigences documentees, les parties prenantes peuvent egalement s'assurer que ces exigences decrivent leurs besoins reels. Puisque le test statique peut etre effectue tot dans le SDLC, une comprehension partagee peut etre creee entre les parties prenantes impliquees. La communication sera egalement amelioree entre les parties prenantes impliquees. Pour cette raison, il est recommande d'impliquer une grande variete de parties prenantes dans le test statique.

Meme si les revues peuvent etre couteuses a mettre en oeuvre, les couts globaux du projet sont generalement bien inferieurs a ceux engendres lorsqu'aucune revue n'est realisee, car moins de temps et d'effort sont necessaires pour corriger les defauts plus tard dans le projet.

Certains defauts de code peuvent etre detectes plus efficacement par l'analyse statique que par le test dynamique, ce qui se traduit generalement par moins de defauts de code et un effort de developpement global moindre.

3.1.3. Differences entre le test statique et le test dynamique

Les pratiques de test statique et de test dynamique se completent mutuellement. Elles ont des objectifs similaires, tels que contribuer a la detection des defauts dans les produits d'activite (voir section 1.1.1), mais il existe egalement des differences, telles que :

  • Le test statique et le test dynamique (avec analyse des defaillances) peuvent tous deux mener a la detection de defauts, cependant certains types de defauts ne peuvent etre trouves que par le test statique ou le test dynamique.
  • Le test statique trouve les defauts directement, tandis que le test dynamique provoque des defaillances a partir desquelles les defauts associes sont determines par une analyse ulterieure
  • Le test statique peut plus facilement detecter des defauts situes sur des chemins dans le code rarement executes ou difficiles a atteindre avec le test dynamique
  • Le test statique peut etre applique aux produits d'activite non executables, tandis que le test dynamique ne peut etre applique qu'aux produits d'activite executables
  • Le test statique peut etre utilise pour mesurer des caracteristiques de qualite qui ne dependent pas de l'execution du code (par exemple, la maintenabilite), tandis que le test dynamique peut etre utilise pour mesurer des caracteristiques de qualite qui dependent de l'execution du code (par exemple, l'efficacite de performance)

Les defauts typiques qui sont plus faciles et/ou moins couteux a trouver par le test statique incluent :

  • Defauts dans les exigences (par exemple, incoherences, ambiguites, contradictions, omissions, inexactitudes, doublons)
  • Defauts de conception (par exemple, structures de base de donnees inefficaces, mauvaise modularisation)
  • Certains types de defauts de codage (par exemple, variables avec des valeurs indefinies, variables non declarees, code inatteignable ou duplique, complexite de code excessive)
  • Ecarts par rapport aux standards (par exemple, non-respect des conventions de nommage dans les standards de codage)
  • Specifications d'interface incorrectes (par exemple, nombre, type ou ordre des parametres ne correspondant pas)
  • Types specifiques de vulnerabilites de securite (par exemple, depassements de tampon)
  • Lacunes ou inexactitudes dans la couverture de la base de test (par exemple, tests manquants pour un critere d'acceptation)
Attention examen

Le code encrypte ou le code executable tiers NE PEUT PAS etre examine par test statique. Seuls les produits d'activite lisibles et comprehensibles peuvent etre revises. L'analyse statique necessite une structure formelle (code source, modeles).

A retenir
  • Le test statique ne necessite PAS l'execution du logiciel (revues + analyse statique)
  • Presque tout produit d'activite peut etre examine (specs, code, plans de test, contrats...)
  • Le test statique trouve les defauts directement, le dynamique provoque des defaillances
  • Le statique detecte des defauts impossibles a trouver en dynamique (code mort, ambiguites)
  • Meme si les revues coutent cher, elles reduisent le cout global du projet

3.2.1. Benefices d'un retour d'information precoce et frequent des parties prenantes

Un retour d'information precoce et frequent permet la communication rapide des problemes de qualite potentiels. S'il y a peu d'implication des parties prenantes pendant le SDLC, le produit en cours de developpement pourrait ne pas correspondre a la vision originale ou actuelle des parties prenantes. Ne pas livrer ce que la partie prenante attend peut entrainer des retravaux couteux, des delais non respectes, des accusations mutuelles, et pourrait meme mener a l'echec complet du projet.

Un retour d'information frequent des parties prenantes tout au long du SDLC peut prevenir les malentendus concernant les exigences et garantir que les changements d'exigences sont compris et implementes plus tot. Cela aide l'equipe de developpement a ameliorer sa comprehension de ce qu'elle construit. Cela leur permet de se concentrer sur les fonctionnalites qui apportent le plus de valeur aux parties prenantes et qui ont l'impact positif le plus important sur les risques identifies.

3.2.2. Activites du processus de revue

La norme ISO/IEC 20246 definit un processus de revue generique qui fournit un cadre structure mais flexible a partir duquel un processus de revue specifique peut etre adapte a une situation particuliere. Si la revue requise est plus formelle, alors davantage de taches decrites pour les differentes activites seront necessaires.

La taille de nombreux produits d'activite les rend trop volumineux pour etre couverts par une seule revue. Le processus de revue peut etre invoque plusieurs fois pour completer la revue de l'ensemble du produit d'activite.

Les activites du processus de revue sont :

  • Planification. Pendant la phase de planification, la portee de la revue doit etre definie, ce qui comprend l'objectif, le produit d'activite a revoir, les caracteristiques de qualite a evaluer, les zones sur lesquelles se concentrer, les criteres de sortie, les informations de support telles que les standards, l'effort et les delais de la revue.
  • Initiation de la revue. Pendant l'initiation de la revue, l'objectif est de s'assurer que toutes les personnes et tous les elements impliques sont prets a demarrer la revue. Cela inclut de s'assurer que chaque participant a acces au produit d'activite en cours de revue, comprend son role et ses responsabilites et recoit tout ce qui est necessaire pour effectuer la revue.
  • Revue individuelle. Chaque reviseur effectue une revue individuelle pour evaluer la qualite du produit d'activite en cours de revue, et pour identifier les anomalies, recommandations et questions en appliquant une ou plusieurs techniques de revue (par exemple, revue basee sur des checklists, revue basee sur des scenarios). La norme ISO/IEC 20246 fournit plus de details sur les differentes techniques de revue. Les reviseurs consignent toutes les anomalies, recommandations et questions identifiees.
  • Communication et analyse. Puisque les anomalies identifiees lors d'une revue ne sont pas necessairement des defauts, toutes ces anomalies doivent etre analysees et discutees. Pour chaque anomalie, une decision doit etre prise concernant son statut, sa responsabilite et les actions requises. Cela se fait generalement lors d'une reunion de revue, au cours de laquelle les participants decident egalement du niveau de qualite du produit d'activite revise et des actions de suivi necessaires. Une revue de suivi peut etre necessaire pour completer les actions.
  • Correction et rapport. Pour chaque defaut, un rapport de defaut doit etre cree afin que les actions correctives puissent etre suivies. Une fois les criteres de sortie atteints, le produit d'activite peut etre accepte. Les resultats de la revue sont rapportes.
Attention examen

Distribuer les documents aux reviseurs = Initiation (etape 2), PAS Planification (etape 1). La planification definit la portee et les criteres, l'initiation distribue les documents et prepare les participants. C'est un piege classique.

3.2.3. Roles et responsabilites dans les revues

Les revues impliquent differentes parties prenantes, qui peuvent assumer plusieurs roles. Les principaux roles et leurs responsabilites sont :

  • Manager – decide ce qui doit etre revise et fournit les ressources, telles que le personnel et le temps pour la revue
  • Auteur – cree et corrige le produit d'activite en cours de revue
  • Moderateur (egalement appele facilitateur) – assure le bon deroulement des reunions de revue, incluant la mediation, la gestion du temps et un environnement de revue sur dans lequel chacun peut s'exprimer librement
  • Scribe (egalement appele secretaire) – rassemble les anomalies des reviseurs et enregistre les informations de revue, telles que les decisions et les nouvelles anomalies trouvees pendant la reunion de revue
  • Reviseur – effectue les revues. Un reviseur peut etre une personne travaillant sur le projet, un expert du domaine ou toute autre partie prenante
  • Responsable de la revue – prend la responsabilite globale de la revue, comme decider qui sera implique et organiser quand et ou la revue aura lieu

D'autres roles plus detailles sont possibles, comme decrit dans la norme ISO/IEC 20246.

3.2.4. Types de revue

Il existe de nombreux types de revue allant des revues informelles aux revues formelles. Le niveau de formalite requis depend de facteurs tels que le SDLC suivi, la maturite du processus de developpement, la criticite et la complexite du produit d'activite revise, les exigences legales ou reglementaires, et le besoin d'une piste d'audit. Le meme produit d'activite peut etre revise avec differents types de revue, par exemple d'abord une revue informelle puis plus tard une plus formelle.

Choisir le bon type de revue est essentiel pour atteindre les objectifs de revue requis (voir section 3.2.5). Le choix n'est pas seulement base sur les objectifs, mais aussi sur des facteurs tels que les besoins du projet, les ressources disponibles, le type de produit d'activite et les risques, le domaine metier et la culture de l'entreprise.

Parmi les types de revue couramment utilises :

  • Revue informelle. Les revues informelles ne suivent pas de processus defini et ne necessitent pas de sortie documentee formelle. L'objectif principal est de detecter des anomalies.
  • Walkthrough (revue guidee). Un walkthrough, dirige par l'auteur, peut servir de nombreux objectifs, tels qu'evaluer la qualite et renforcer la confiance dans le produit d'activite, former les reviseurs, obtenir un consensus, generer de nouvelles idees, motiver et permettre aux auteurs de s'ameliorer et detecter des anomalies. Les reviseurs peuvent effectuer une revue individuelle avant le walkthrough, mais ce n'est pas obligatoire.
  • Revue technique. Une revue technique est realisee par des reviseurs techniquement qualifies et dirigee par un moderateur. Les objectifs d'une revue technique sont d'obtenir un consensus et de prendre des decisions concernant un probleme technique, mais aussi de detecter des anomalies, d'evaluer la qualite et de renforcer la confiance dans le produit d'activite, de generer de nouvelles idees et de motiver et permettre aux auteurs de s'ameliorer.
  • Inspection. Les inspections etant le type de revue le plus formel, elles suivent le processus generique complet (voir section 3.2.2). L'objectif principal est de trouver le nombre maximum d'anomalies. Les autres objectifs sont d'evaluer la qualite, de renforcer la confiance dans le produit d'activite et de motiver et permettre aux auteurs de s'ameliorer. Des metriques sont collectees et utilisees pour ameliorer le SDLC, y compris le processus d'inspection. Lors des inspections, l'auteur ne peut pas agir en tant que responsable de la revue ou scribe.
Attention examen

Walkthrough = dirige par l'AUTEUR. Inspection = dirige par un FACILITATEUR forme. Lors d'une inspection, l'auteur ne peut PAS etre responsable de la revue ni scribe. Toujours se rappeler qui dirige chaque type de revue.

3.2.5. Facteurs de succes des revues

Plusieurs facteurs determinent le succes des revues, notamment :

  • Definir des objectifs clairs et des criteres de sortie mesurables. L'evaluation des participants ne doit jamais etre un objectif
  • Choisir le type de revue approprie pour atteindre les objectifs donnes, et adapte au type de produit d'activite, aux participants de la revue, aux besoins et au contexte du projet
  • Effectuer les revues sur de petites portions, afin que les reviseurs ne perdent pas leur concentration pendant une revue individuelle et/ou la reunion de revue (lorsqu'elle a lieu)
  • Fournir un retour d'information des revues aux parties prenantes et aux auteurs afin qu'ils puissent ameliorer le produit et leurs activites (voir section 3.2.1)
  • Accorder un temps suffisant aux participants pour se preparer a la revue
  • Soutien du management pour le processus de revue
  • Integrer les revues dans la culture de l'organisation, pour promouvoir l'apprentissage et l'amelioration des processus
  • Fournir une formation adequate a tous les participants afin qu'ils sachent comment remplir leur role
  • Faciliter les reunions

Produits examinables par test statique

  • Specifications d'exigences, user stories, epics
  • Code source
  • Plans de test, cas de test, procedures de test
  • Documents de conception (architecture, diagrammes)
  • Contrats, plans de projet, calendriers
Ce qui NE PEUT PAS etre revise par test statique : code compile/encrypte (non lisible par un humain), code executable tiers.

Processus de revue : 5 etapes dans l'ordre

1. Planification → 2. Initiation de la revue → 3. Revue individuelle → 4. Communication et analyse → 5. Correction et rapport

1. PlanificationDefinir la portee, les criteres, l'effort, les roles, les criteres d'entree/sortie
2. Initiation de la revueDistribuer le produit d'activite et les supports aux reviseurs, expliquer la portee et les objectifs

Comment retenir l'ordre du processus de revue
  1. Planification — on decide QUOI revoir, QUI participe, QUAND
  2. Initiation — on DISTRIBUE le document aux reviseurs
  3. Revue individuelle — chacun EXAMINE seul le document
  4. Communication — on se REUNIT pour discuter des anomalies
  5. Correction — on CORRIGE les defauts et on RAPPORTE
Moyen mnemotechnique : P-I-R-C-C = "PIRate ca Corrige !" — Planifier, Initier, Revoir, Communiquer, Corriger.
Piege : La question decrit les 5 activites dans le desordre et te demande la bonne sequence. Identifie chaque description : "distribuer les documents" = Initiation (pas Planification !).

Facteurs de succes des revues

  • Objectifs clairs definis a l'avance
  • Choisir le bon type de revue selon les objectifs
  • Les reviseurs ont suffisamment de temps pour preparer
  • Le management soutient le processus de revue
  • Les revues font partie de la culture d'entreprise
  • Formation adequate des participants
  • Diviser les grands documents en petites parties
  • Les defauts trouves sont reconnus et traites objectivement (pas de blame)

Attention : lors des revues, on trouve des DEFAUTS, pas des defaillances ! Les defaillances apparaissent uniquement lors de l'execution (test dynamique).
