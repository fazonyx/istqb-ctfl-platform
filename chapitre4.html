Partitions d'equivalence (EP)

  • Diviser les entrees en groupes (partitions) ou le systeme se comporte de la meme maniere
  • Partition valide : valeurs acceptees par le systeme
  • Partition invalide : valeurs rejetees par le systeme
  • Chaque valeur appartient a exactement UNE partition
  • Un seul cas de test par partition suffit (representant)
Couverture EP = partitions testees / total partitions x 100%

Exemple : champ age 18-65. Partitions : <18 (invalide), 18-65 (valide), >65 (invalide). 3 partitions au total.

Comment resoudre un exercice EP en 4 etapes
  1. Identifier la variable d'entree et ses contraintes (ex: "age entre 18 et 65")
  2. Lister les partitions : une valide (18-65), les invalides (<18, >65). S'il y a des sous-regles, creer des partitions supplementaires
  3. Choisir un representant par partition (n'importe quelle valeur dans la plage : 25 pour 18-65, 10 pour <18, 70 pour >65)
  4. Compter : couverture = partitions testees / total partitions x 100%
Exemple : D = CY - BY. Partitions : D<0 (erreur), 0<=D<18 (etudiant), 18<=D<65 (normal), D>=65 (retraite) = 4 partitions. Si 2 sont deja couvertes, il faut 2 tests supplementaires.
Piege : Lis bien les bornes ! "depasse 100$" signifie >100, pas >=100. "entre 0 et 2 inclus" signifie 0, 1 et 2 sont dans la partition.

BVA 2 valeurs (par defaut dans le syllabus)

  • Pour chaque frontiere entre 2 partitions : 2 valeurs (une de chaque cote)
  • Exemple : frontiere entre <18 et 18-65 a la valeur 18 : tester 17 et 18
  • Exemple : frontiere entre 18-65 et >65 a la valeur 65 : tester 65 et 66
  • Total : 2 frontieres x 2 valeurs = 4 valeurs limites

BVA 3 valeurs

  • Pour chaque frontiere : 3 valeurs (frontiere + 1 de chaque cote)
  • Exemple frontiere a 18 : tester 17, 18, 19
  • Exemple frontiere a 65 : tester 64, 65, 66
  • Total : 2 frontieres x 3 valeurs = 6 valeurs limites (en eliminant les doublons)
Couverture BVA = valeurs limites testees / total valeurs limites x 100%
Comment resoudre un exercice BVA en 3 etapes
  1. Identifier les frontieres entre partitions (la ou le comportement change)
  2. Pour BVA 2-valeurs : pour chaque frontiere, prendre la valeur juste en-dessous et juste au-dessus (ex: frontiere a 18 → tester 17 et 18)
  3. Pour BVA 3-valeurs : pour chaque frontiere, prendre la frontiere + 1 de chaque cote (ex: frontiere a 18 → tester 17, 18, 19)
Exemple BVA 2-val : Partitions <0, 0-2, >2. Frontieres a 0 et 2.
Frontiere 0 : tester -1 et 0. Frontiere 2 : tester 2 et 3.
Total : 4 valeurs limites = {-1, 0, 2, 3}. Si tu testes les 4 → 100% couverture BVA.
Piege : Ne confonds pas BVA 2-valeurs et 3-valeurs ! Le syllabus utilise 2-valeurs par defaut. Si la question dit "two-value BVA", c'est 2 valeurs par frontiere, pas 3.

Tables de decision

  • Conditions : les entrees/situations (lignes du haut)
  • Actions : les sorties/resultats attendus (lignes du bas)
  • Regles : chaque colonne = une combinaison unique de conditions avec ses actions
  • Nombre de regles theorique = 2^n (n = nombre de conditions booleennes)
Couverture table de decision = regles testees / total regles x 100%
Pour identifier quelle regle couvre un cas de test : verifier la combinaison de conditions et trouver la colonne correspondante.
Comment resoudre un exercice de table de decision
  1. Lire le cas de test : extraire les valeurs de chaque condition (ex: "19 ans, non inscrit, sans experience")
  2. Mapper chaque condition a la ligne correspondante de la table (Age=19-65, Inscrit=NON, Exp=0-4)
  3. Trouver la colonne ou TOUTES les conditions correspondent → c'est la regle couverte
  4. Pour la couverture : compter combien de colonnes/regles sont couvertes par l'ensemble des cas de test
Exemple : TC: homme de 66 ans, non inscrit. Dans la table : Age >65, Inscrit=NON. Chercher la colonne avec >65 et NON → c'est R4.

Transitions d'etat

  • Etat : situation dans laquelle le systeme se trouve
  • Transition : changement d'un etat a un autre
  • Evenement : ce qui declenche une transition
  • Action : ce qui resulte d'une transition
  • Garde : condition supplementaire pour qu'une transition ait lieu
Couverture transitions = transitions executees / total transitions valides x 100%
Comment resoudre un exercice de transitions d'etat
  1. Dessiner le graphe a partir de la table : etats = cercles, transitions = fleches avec evenements
  2. Lister toutes les transitions valides (compter les fleches distinctes)
  3. Tracer le chemin du cas de test en suivant les evenements un par un depuis l'etat initial
  4. Compter les transitions distinctes couvertes par le chemin
  5. Verifier la faisabilite : apres un etat final (End), plus aucune transition n'est possible !
Exemple : Sequence "Available, ChangeRoom, NotAvailable, Available, Pay"
S1→S2 (Available) → S2→S1 (ChangeRoom) → S1→S3 (NotAvailable) → S3→S2 (Available) → S2→S4 (Pay)
= 5 transitions distinctes couvertes sur 7 = 71% couverture.
Piege : Un meme evenement peut correspondre a des transitions DIFFERENTES selon l'etat de depart ! "Available" depuis S1 (→S2) n'est PAS la meme transition que "Available" depuis S3 (→S2).

Couverture des instructions

  • Chaque instruction du code executee au moins une fois
  • Mesure : instructions executees / total instructions x 100%
100% couverture instructions NE GARANTIT PAS 100% couverture branches ! Une branche "else" vide peut ne pas etre testee.

Couverture des branches

  • Chaque branche (vrai ET faux) de chaque decision executee au moins une fois
  • Mesure : branches executees / total branches x 100%
100% branches → 100% instructions (garanti) | 100% instructions ↗ 100% branches (PAS garanti)
Comment verifier la couverture d'instructions et de branches
  1. Tracer le chemin du cas de test dans le code (quelles lignes sont executees)
  2. Instructions : cocher chaque ligne executee. Couverture = lignes cochees / total lignes
  3. Branches : pour chaque IF/decision, verifier si le chemin VRAI et le chemin FAUX ont ete empruntes
  4. Rappel : 100% branches garantit 100% instructions. L'inverse est FAUX.
Piege : Un IF sans ELSE a quand meme 2 branches (vrai et faux). Si tu ne testes que le cas vrai, tu as 100% instructions mais seulement 50% branches.

Error guessing (Supposition d'erreurs)

  • Le testeur utilise son experience pour anticiper les erreurs, defauts et defaillances
  • Base sur : defauts passes, erreurs typiques des developpeurs, types de defaillances connues
  • Cree des "listes de bugs" ou "attaques" (taxonomies de defauts)
Error guessing n'anticipe PAS les causes racines ! Il anticipe les erreurs, defauts et defaillances.

Test exploratoire

  • Conception, execution et evaluation des tests simultanement
  • Utilise des chartes de test (session-based)
  • Peut utiliser des techniques boite noire pendant l'exploration
  • Ideal quand les specifications sont limitees ou le temps est court
Le test exploratoire ne permet PAS de predire de maniere fiable le nombre de defauts restants (pas de metriques de couverture formelles).

Test base sur des checklists

Le testeur utilise une liste de conditions a verifier. Les checklists sont construites a partir de l'experience, des standards, ou des defauts connus. La couverture peut etre imprecise car les items sont souvent a un niveau d'abstraction eleve.

User stories : Card, Conversation, Confirmation

  • Card : Support physique ou numerique decrivant la user story
  • Conversation : Echanges entre equipe pour clarifier les details
  • Confirmation : Criteres d'acceptation utilises pour confirmer que la story est complete

Collaboration pour comprendre ce qui doit etre livre : les user stories sont creees ENSEMBLE par representants metier, developpeurs et testeurs.

Criteres d'acceptation : INVEST et Given/When/Then

  • INVEST : Independent, Negotiable, Valuable, Estimable, Small, Testable
  • Given/When/Then : Given [contexte initial], When [action], Then [resultat attendu]
