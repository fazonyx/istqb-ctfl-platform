4.1. Vue d'ensemble des techniques de test

Objectifs d'apprentissage :
FL-4.1.1 (K2) Distinguer les techniques de test boite noire, les techniques de test boite blanche et les techniques de test basees sur l'experience

Les techniques de test aident le testeur dans l'analyse de test (quoi tester) et dans la conception de test (comment tester). Les techniques de test contribuent a developper un ensemble de cas de test relativement restreint mais suffisant, de maniere systematique. Les techniques de test aident egalement le testeur a definir les conditions de test, a identifier les elements de couverture et a identifier les donnees de test pendant l'analyse et la conception des tests. Des informations complementaires sur les techniques de test se trouvent dans la norme ISO/IEC/IEEE 29119-4 et dans (Beizer 1990, Craig 2002, Copeland 2004, Koomen 2006, Jorgensen 2014, Ammann 2016, Forgacs 2019).

Dans ce syllabus, les techniques de test sont classees en boite noire, boite blanche et basees sur l'experience.

Les techniques de test boite noire (egalement appelees techniques basees sur les specifications) reposent sur une analyse du comportement specifie de l'objet de test sans reference a sa structure interne. Par consequent, les cas de test sont independants de la facon dont le logiciel est implemente. En consequence, si l'implementation change mais que le comportement requis reste le meme, les cas de test restent utiles.

Les techniques de test boite blanche (egalement appelees techniques basees sur la structure) reposent sur une analyse de la structure interne et du traitement de l'objet de test. Comme les cas de test dependent de la conception du logiciel, ils ne peuvent etre crees qu'apres la conception ou l'implementation de l'objet de test.

Les techniques de test basees sur l'experience utilisent efficacement les connaissances et l'experience des testeurs pour la conception et l'implementation des cas de test. L'efficacite de ces techniques depend fortement des competences du testeur. Les techniques basees sur l'experience peuvent detecter des defauts qui pourraient etre manques par les techniques boite noire et boite blanche. Ainsi, les techniques basees sur l'experience sont complementaires aux techniques boite noire et boite blanche.

4.2. Techniques de test boite noire

Objectifs d'apprentissage :
FL-4.2.1 (K3) Utiliser les partitions d'equivalence pour deriver des cas de test
FL-4.2.2 (K3) Utiliser l'analyse des valeurs limites pour deriver des cas de test
FL-4.2.3 (K3) Utiliser le test par table de decision pour deriver des cas de test
FL-4.2.4 (K3) Utiliser le test de transition d'etat pour deriver des cas de test

Les techniques de test boite noire couramment utilisees, presentees dans les sections suivantes, sont :

  • Partitions d'equivalence
  • Analyse des valeurs limites
  • Test par table de decision
  • Test de transition d'etat

4.2.1. Partitions d'equivalence

Les partitions d'equivalence (EP) divisent les donnees en partitions (appelees partitions d'equivalence) en se basant sur l'attente que tous les elements d'une partition donnee seront traites de la meme maniere par l'objet de test. La theorie derriere cette technique est que si un cas de test, qui teste une valeur d'une partition d'equivalence, detecte un defaut, ce defaut devrait egalement etre detecte par des cas de test testant toute autre valeur de la meme partition. Par consequent, un seul test pour chaque partition est suffisant.

Les partitions d'equivalence peuvent etre identifiees pour tout element de donnees lie a l'objet de test, y compris les entrees, les sorties, les elements de configuration, les valeurs internes, les valeurs liees au temps et les parametres d'interface. Les partitions peuvent etre continues ou discretes, ordonnees ou non ordonnees, finies ou infinies. Les partitions ne doivent pas se chevaucher et doivent etre des ensembles non vides.

Pour des elements de test simples, l'EP peut etre facile, mais en pratique, comprendre comment l'objet de test traitera differentes valeurs est souvent complique. Par consequent, le partitionnement doit etre fait avec soin.

Une partition contenant des valeurs valides est appelee partition valide. Une partition contenant des valeurs invalides est appelee partition invalide. Les definitions des valeurs valides et invalides peuvent varier selon les equipes et les organisations. Par exemple, les valeurs valides peuvent etre interpretees comme celles qui doivent etre traitees par l'objet de test ou celles pour lesquelles la specification definit leur traitement. Les valeurs invalides peuvent etre interpretees comme celles qui doivent etre ignorees ou rejetees par l'objet de test ou celles pour lesquelles aucun traitement n'est defini dans la specification de l'objet de test.

En EP, les elements de couverture sont les partitions d'equivalence. Pour atteindre 100% de couverture avec cette technique, les cas de test doivent exercer toutes les partitions identifiees (y compris les partitions invalides) en couvrant chaque partition au moins une fois. La couverture est mesuree comme le nombre de partitions exercees par au moins un cas de test, divise par le nombre total de partitions identifiees, et est exprimee en pourcentage.

De nombreux elements de test incluent plusieurs ensembles de partitions (par exemple, des elements de test avec plus d'un parametre d'entree), ce qui signifie qu'un cas de test couvrira des partitions de differents ensembles de partitions. Le critere de couverture le plus simple dans le cas de plusieurs ensembles de partitions est appele couverture Each Choice (Ammann 2016). La couverture Each Choice exige que les cas de test exercent chaque partition de chaque ensemble de partitions au moins une fois. La couverture Each Choice ne prend pas en compte les combinaisons de partitions.

4.2.2. Analyse des valeurs limites

L'analyse des valeurs limites (BVA) est une technique de test basee sur l'exercice des limites des partitions d'equivalence. Par consequent, la BVA ne peut etre utilisee que pour des partitions ordonnees. Les valeurs minimale et maximale d'une partition sont ses valeurs limites. Dans le cas de la BVA, si deux elements appartiennent a la meme partition, tous les elements entre eux doivent egalement appartenir a cette partition.

La BVA se concentre sur les valeurs limites des partitions car les developpeurs sont plus susceptibles de faire des erreurs avec ces valeurs limites. Les defauts typiques trouves par la BVA sont situes la ou les limites implementees sont deplacees au-dessus ou en dessous de leurs positions prevues ou sont completement omises.

Ce syllabus couvre deux versions de la BVA : la BVA a 2 valeurs et la BVA a 3 valeurs. Elles different en termes d'elements de couverture par limite devant etre exerces pour atteindre 100% de couverture.

En BVA a 2 valeurs (Craig 2002, Myers 2011), pour chaque valeur limite il y a deux elements de couverture : cette valeur limite et son voisin le plus proche appartenant a la partition adjacente. Pour atteindre 100% de couverture avec la BVA a 2 valeurs, les cas de test doivent exercer tous les elements de couverture, c'est-a-dire toutes les valeurs limites identifiees. La couverture est mesuree comme le nombre de valeurs limites exercees, divise par le nombre total de valeurs limites identifiees, et est exprimee en pourcentage.

En BVA a 3 valeurs (Koomen 2006, O'Regan 2019), pour chaque valeur limite il y a trois elements de couverture : cette valeur limite et ses deux voisins. Par consequent, en BVA a 3 valeurs, certains des elements de couverture peuvent ne pas etre des valeurs limites. Pour atteindre 100% de couverture avec la BVA a 3 valeurs, les cas de test doivent exercer tous les elements de couverture, c'est-a-dire les valeurs limites identifiees et leurs voisins. La couverture est mesuree comme le nombre de valeurs limites et de voisins exerces, divise par le nombre total de valeurs limites et de voisins identifies, et est exprimee en pourcentage.

La BVA a 3 valeurs est plus rigoureuse que la BVA a 2 valeurs car elle peut detecter des defauts negliges par la BVA a 2 valeurs. Par exemple, si la decision "if (x ≤ 10) ..." est incorrectement implementee comme "if (x = 10) ...", aucune donnee de test derivee de la BVA a 2 valeurs (x = 10, x = 11) ne peut detecter le defaut. Cependant, x = 9, derive de la BVA a 3 valeurs, est susceptible de le detecter.

4.2.3. Test par table de decision

Les tables de decision sont utilisees pour tester l'implementation d'exigences qui specifient comment differentes combinaisons de conditions produisent differents resultats. Les tables de decision sont un moyen efficace d'enregistrer une logique complexe, comme les regles metier.

Lors de la creation de tables de decision, les conditions et les actions resultantes du systeme sont definies. Celles-ci forment les lignes de la table. Chaque colonne correspond a une regle de decision qui definit une combinaison unique de conditions, accompagnee des actions associees. Dans les tables de decision a entrees limitees, toutes les valeurs des conditions et des actions (sauf celles qui sont non pertinentes ou infaisables ; voir ci-dessous) sont representees comme des valeurs booleennes (vrai ou faux). Alternativement, dans les tables de decision a entrees etendues, certaines ou toutes les conditions et actions peuvent egalement prendre plusieurs valeurs (par exemple, des plages de nombres, des partitions d'equivalence, des valeurs discretes).

La notation pour les conditions est la suivante : "T" (true/vrai) signifie que la condition est satisfaite. "F" (false/faux) signifie que la condition n'est pas satisfaite. "–" signifie que la valeur de la condition est non pertinente pour le resultat de l'action. "N/A" signifie que la condition est infaisable pour une regle donnee. Pour les actions : "X" signifie que l'action doit se produire. Un espace vide signifie que l'action ne doit pas se produire. D'autres notations peuvent egalement etre utilisees.

Une table de decision complete a suffisamment de colonnes pour couvrir chaque combinaison de conditions. La table peut etre simplifiee en supprimant les colonnes contenant des combinaisons infaisables de conditions. La table peut egalement etre minimisee en fusionnant les colonnes dans lesquelles certaines conditions n'affectent pas le resultat en une seule colonne. Les algorithmes de minimisation des tables de decision sont hors du perimetre de ce syllabus.

Dans le test par table de decision, les elements de couverture sont les colonnes contenant des combinaisons faisables de conditions. Pour atteindre 100% de couverture avec cette technique, les cas de test doivent exercer toutes ces colonnes. La couverture est mesuree comme le nombre de colonnes exercees, divise par le nombre total de colonnes faisables, et est exprimee en pourcentage.

La force du test par table de decision est qu'il fournit une approche systematique pour identifier toutes les combinaisons de conditions, dont certaines pourraient autrement etre negligees. Il aide egalement a trouver les lacunes ou contradictions dans les exigences. S'il y a de nombreuses conditions, exercer toutes les regles de decision peut etre chronophage, car le nombre de regles croit exponentiellement avec le nombre de conditions. Dans ce cas, pour reduire le nombre de regles a exercer, une table de decision minimisee ou une approche basee sur les risques peut etre utilisee.

4.2.4. Test de transition d'etat

Un diagramme d'etat modelise le comportement d'un systeme en montrant ses etats possibles et les transitions d'etat valides. Une transition est initiee par un evenement, qui peut etre en plus qualifie par une condition de garde. Les transitions sont supposees etre instantanees et peuvent parfois entrainer une action du logiciel. La syntaxe courante d'etiquetage des transitions est la suivante : "evenement [condition de garde] / action". Les conditions de garde et les actions peuvent etre omises si elles n'existent pas ou ne sont pas pertinentes pour le testeur.

Une table d'etat est un modele equivalent a un diagramme d'etat. Ses lignes representent les etats et ses colonnes representent les evenements (ainsi que les conditions de garde si elles existent). Les entrees de la table (cellules) representent les transitions et contiennent l'etat cible, ainsi que les actions resultantes, si elles sont definies. Contrairement au diagramme d'etat, la table d'etat montre explicitement les transitions invalides, representees par des cellules vides.

Un cas de test base sur un diagramme d'etat ou une table d'etat est generalement represente comme une sequence d'evenements, qui aboutit a une sequence de changements d'etat (et d'actions, si necessaire). Un cas de test peut, et le fait generalement, couvrir plusieurs transitions entre etats.

Il existe de nombreux criteres de couverture pour le test de transition d'etat. Ce syllabus en presente trois.

En couverture de tous les etats, les elements de couverture sont les etats. Pour atteindre 100% de couverture de tous les etats, les cas de test doivent s'assurer que tous les etats sont exerces. La couverture est mesuree comme le nombre d'etats exerces divise par le nombre total d'etats et est exprimee en pourcentage.

En couverture des transitions valides (egalement appelee couverture 0-switch), les elements de couverture sont les transitions valides individuelles. Pour atteindre 100% de couverture des transitions valides, les cas de test doivent exercer toutes les transitions valides. La couverture est mesuree comme le nombre de transitions valides exercees divise par le nombre total de transitions valides et est exprimee en pourcentage.

En couverture de toutes les transitions, les elements de couverture sont toutes les transitions figurant dans une table d'etat. Pour atteindre 100% de couverture de toutes les transitions, les cas de test doivent exercer toutes les transitions valides et tenter d'executer les transitions invalides. Tester une seule transition invalide par cas de test permet d'eviter le masquage de defauts, c'est-a-dire une situation dans laquelle un defaut empeche la detection d'un autre. La couverture est mesuree comme le nombre de transitions valides et invalides exercees ou tentees par les cas de test executes, divise par le nombre total de transitions valides et invalides, et est exprimee en pourcentage.

La couverture de tous les etats est plus faible que la couverture des transitions valides, car elle peut generalement etre atteinte sans exercer toutes les transitions. La couverture des transitions valides est le critere de couverture le plus largement utilise. Atteindre une couverture complete des transitions valides garantit une couverture complete de tous les etats. Atteindre une couverture complete de toutes les transitions garantit a la fois la couverture complete de tous les etats et la couverture complete des transitions valides, et devrait etre une exigence minimale pour les logiciels critiques en termes de mission et de securite.

4.3. Techniques de test boite blanche

Objectifs d'apprentissage :
FL-4.3.1 (K2) Expliquer le test des instructions
FL-4.3.2 (K2) Expliquer le test des branches
FL-4.3.3 (K2) Expliquer la valeur du test boite blanche

En raison de leur popularite et de leur simplicite, cette section se concentre sur deux techniques de test boite blanche liees au code :

  • Test des instructions
  • Test des branches

Il existe des techniques de test boite blanche plus rigoureuses qui sont utilisees dans certains environnements critiques pour la securite, la mission ou a haute integrite pour atteindre une couverture de code plus approfondie. Il existe egalement des techniques de test boite blanche utilisees a des niveaux de test superieurs (par exemple, le test d'API), ou utilisant une couverture non liee au code (par exemple, la couverture de neurones dans le test de reseaux de neurones). Ces techniques ne sont pas abordees dans ce syllabus.

4.3.1. Test des instructions et couverture des instructions

Dans le test des instructions, les elements de couverture sont les instructions executables. L'objectif est de concevoir des cas de test qui exercent les instructions dans le code jusqu'a ce qu'un niveau de couverture acceptable soit atteint. La couverture est mesuree comme le nombre d'instructions exercees par les cas de test divise par le nombre total d'instructions executables dans le code, et est exprimee en pourcentage.

Lorsque 100% de couverture des instructions est atteinte, cela garantit que toutes les instructions executables du code ont ete exercees au moins une fois. En particulier, cela signifie que chaque instruction contenant un defaut sera executee, ce qui peut provoquer une defaillance demontrant la presence du defaut. Cependant, exercer une instruction avec un cas de test ne detectera pas les defauts dans tous les cas. Par exemple, cela peut ne pas detecter les defauts dependant des donnees (par exemple, une division par zero qui n'echoue que lorsqu'un denominateur est mis a zero). De plus, 100% de couverture des instructions ne garantit pas que toute la logique de decision a ete testee car, par exemple, cela peut ne pas exercer toutes les branches (voir chapitre 4.3.2) du code.

4.3.2. Test des branches et couverture des branches

Une branche est un transfert de controle entre deux noeuds dans le graphe de flux de controle, qui montre les sequences possibles dans lesquelles les instructions du code source sont executees dans l'objet de test. Chaque transfert de controle peut etre soit inconditionnel (c'est-a-dire du code lineaire) soit conditionnel (c'est-a-dire un resultat de decision).

Dans le test des branches, les elements de couverture sont les branches et l'objectif est de concevoir des cas de test pour exercer les branches dans le code jusqu'a ce qu'un niveau de couverture acceptable soit atteint. La couverture est mesuree comme le nombre de branches exercees par les cas de test divise par le nombre total de branches et est exprimee en pourcentage.

Lorsque 100% de couverture des branches est atteinte, toutes les branches du code, inconditionnelles et conditionnelles, sont exercees par les cas de test. Les branches conditionnelles correspondent generalement a un resultat vrai ou faux d'une decision "if...then", a un resultat d'une instruction switch/case, ou a une decision de sortir ou de continuer dans une boucle. Cependant, exercer une branche avec un cas de test ne detectera pas les defauts dans tous les cas. Par exemple, cela peut ne pas detecter les defauts necessitant l'execution d'un chemin specifique dans le code.

La couverture des branches subsume la couverture des instructions. Cela signifie que tout ensemble de cas de test atteignant 100% de couverture des branches atteint egalement 100% de couverture des instructions (mais pas l'inverse).

4.3.3. La valeur du test boite blanche

Une force fondamentale que toutes les techniques de test boite blanche partagent est que l'ensemble de l'implementation logicielle est prise en compte pendant les tests, ce qui facilite la detection des defauts meme lorsque la specification du logiciel est vague, obsolete ou incomplete. Une faiblesse correspondante est que si le logiciel n'implemente pas une ou plusieurs exigences, le test boite blanche peut ne pas detecter les defauts d'omission resultants (Watson 1996).

Les techniques de test boite blanche peuvent etre utilisees en test statique (par exemple, lors de revues a sec du code). Elles sont bien adaptees a la revue de code pas encore pret pour l'execution (Hetzel 1988), de pseudocode et d'autres logiques de haut niveau ou descendantes pouvant etre modelisees avec un graphe de flux de controle.

Effectuer uniquement du test boite noire ne fournit pas de mesure de la couverture reelle du code. Les mesures de couverture boite blanche fournissent une mesure objective de la couverture et les informations necessaires pour permettre la generation de tests supplementaires afin d'augmenter cette couverture, et par consequent renforcer la confiance dans le code.

4.4. Techniques de test basees sur l'experience

Objectifs d'apprentissage :
FL-4.4.1 (K2) Expliquer la prediction d'erreurs
FL-4.4.2 (K2) Expliquer le test exploratoire
FL-4.4.3 (K2) Expliquer le test base sur des checklists

Les techniques de test basees sur l'experience couramment utilisees, presentees dans les sections suivantes, sont :

  • Prediction d'erreurs
  • Test exploratoire
  • Test base sur des checklists

4.4.1. Prediction d'erreurs

La prediction d'erreurs est une technique de test utilisee pour anticiper l'occurrence d'erreurs, de defauts et de defaillances, basee sur les connaissances du testeur, notamment :

  • Comment l'application a fonctionne par le passe
  • Les types d'erreurs que les developpeurs ont tendance a commettre et les types de defauts qui resultent de ces erreurs
  • Les types de defaillances qui se sont produites dans d'autres applications similaires

En general, les erreurs, defauts et defaillances peuvent etre lies a : l'entree (par exemple, une entree correcte non acceptee, des parametres errones ou manquants), la sortie (par exemple, un format errone, un resultat errone), la logique (par exemple, des cas manquants, un operateur errone), le calcul (par exemple, un operande incorrect, un calcul errone), les interfaces (par exemple, une incompatibilite de parametres, des types incompatibles), ou les donnees (par exemple, une initialisation incorrecte, un type errone).

Les attaques par fautes sont une maniere d'implementer la prediction d'erreurs. Cette technique de test exige que le testeur cree ou acquiere une liste d'erreurs, de defauts et de defaillances possibles, et concoive des tests qui identifieront les defauts associes aux erreurs, exposeront les defauts ou provoqueront les defaillances. Ces listes peuvent etre construites a partir de l'experience, des donnees de defauts et de defaillances, ou des connaissances generales sur les raisons pour lesquelles les logiciels echouent.

4.4.2. Test exploratoire

Dans le test exploratoire, les tests sont simultanement concus, executes et evalues pendant que le testeur decouvre l'objet de test. Le test est utilise pour en apprendre davantage sur l'objet de test, pour l'explorer plus en profondeur avec des tests cibles, et pour creer des tests pour les zones non testees.

Le test exploratoire est parfois realise en utilisant le test base sur des sessions pour structurer les tests. Dans une approche basee sur des sessions, le test exploratoire est effectue dans un cadre temporel defini. Le testeur utilise une charte de test contenant les objectifs de test pour guider les tests. La session de test est generalement suivie d'un debriefing impliquant une discussion entre le testeur et les parties prenantes interessees par les resultats de la session de test. Dans cette approche, les objectifs de test peuvent etre traites comme des conditions de test de haut niveau. Les elements de couverture sont identifies et exerces pendant la session de test. Le testeur peut utiliser des fiches de session de test pour documenter les etapes suivies et les decouvertes faites.

Le test exploratoire est utile lorsqu'il y a peu ou pas de specifications adequates ou lorsqu'il y a une pression temporelle importante sur les tests. Le test exploratoire est egalement utile pour completer d'autres techniques de test plus formelles. Le test exploratoire sera plus efficace si le testeur est experimente, possede une connaissance du domaine et un haut degre de competences essentielles, comme les capacites analytiques, la curiosite et la creativite (voir section 1.5.1).

Le test exploratoire peut incorporer l'utilisation d'autres techniques de test (par exemple, les partitions d'equivalence). Plus d'informations sur le test exploratoire se trouvent dans (Kaner 1999, Whittaker 2009, Hendrickson 2013).

4.4.3. Test base sur des checklists

Dans le test base sur des checklists, un testeur concoit, implemente et execute des tests pour couvrir les conditions de test a partir d'une checklist. Les checklists peuvent etre construites a partir de l'experience, de la connaissance de ce qui est important pour l'utilisateur, ou d'une comprehension de pourquoi et comment les logiciels echouent. Les checklists ne doivent pas contenir d'elements pouvant etre verifies automatiquement, d'elements mieux adaptes comme criteres d'entree ou de sortie, ou d'elements trop generaux (Brykczynski 1999).

Les elements de checklist sont souvent formules sous forme de question. Il doit etre possible de verifier chaque element separement et directement. Ces elements peuvent se referer a des exigences, des proprietes d'interface graphique, des caracteristiques de qualite ou d'autres formes de conditions de test. Les checklists peuvent etre creees pour supporter differents types de tests, y compris les tests fonctionnels et non fonctionnels (par exemple, les 10 heuristiques pour les tests d'utilisabilite (Nielsen 1994)).

Certains elements de checklist peuvent progressivement devenir moins efficaces au fil du temps car les developpeurs apprendront a eviter de commettre les memes erreurs. De nouveaux elements peuvent egalement devoir etre ajoutes pour refleter les defauts de haute severite nouvellement trouves. Par consequent, les checklists doivent etre regulierement mises a jour en fonction de l'analyse des defauts. Cependant, il faut veiller a ne pas laisser la checklist devenir trop longue (Gawande 2009).

En l'absence de cas de test detailles, le test base sur des checklists peut fournir des lignes directrices et un certain degre de coherence pour les tests. Si les checklists sont de haut niveau, une certaine variabilite dans les tests reels est susceptible de se produire, entrainant potentiellement une couverture plus grande mais moins de repetabilite.

4.5. Approches de test basees sur la collaboration

Objectifs d'apprentissage :
FL-4.5.1 (K2) Expliquer comment rediger des user stories en collaboration avec les developpeurs et les representants metier
FL-4.5.2 (K2) Classifier les differentes options pour rediger des criteres d'acceptation
FL-4.5.3 (K3) Utiliser le developpement pilote par les tests d'acceptation (ATDD) pour deriver des cas de test

Chacune des techniques de test mentionnees ci-dessus (voir sections 4.2, 4.3, 4.4) a un objectif particulier en matiere de detection des defauts. Les approches basees sur la collaboration, en revanche, se concentrent egalement sur l'evitement des defauts par la collaboration et la communication.

4.5.1. Redaction collaborative de user stories

Une user story represente une fonctionnalite qui sera precieuse pour un utilisateur ou un acheteur d'un systeme ou d'un logiciel. Les user stories ont trois aspects essentiels (Jeffries 2000), appeles ensemble les "3 C" :

  • Carte (Card) – le support decrivant une user story (par exemple, une fiche cartonnee, une entree dans un tableau electronique)
  • Conversation – explique comment le logiciel sera utilise (peut etre documentee ou verbale)
  • Confirmation – les criteres d'acceptation (voir section 4.5.2)

Le format le plus courant pour une user story est "En tant que [role], je veux [objectif a accomplir], afin de [valeur metier resultante pour le role]", suivi des criteres d'acceptation.

La redaction collaborative de la user story peut utiliser des techniques telles que le brainstorming et le mind mapping. La collaboration permet a l'equipe d'obtenir une vision partagee de ce qui doit etre livre, en tenant compte de trois perspectives : metier, developpement et test.

Les bonnes user stories doivent etre : Independantes, Negociables, ayant de la Valeur, Estimables, de petite taille (Small) et Testables (INVEST). Si une partie prenante ne sait pas comment tester une user story, cela peut indiquer que la user story n'est pas assez claire, qu'elle ne reflete pas quelque chose de valeur pour elle, ou que la partie prenante a simplement besoin d'aide pour les tests (Wake 2003).

4.5.2. Criteres d'acceptation

Les criteres d'acceptation d'une user story sont les conditions qu'une implementation de la user story doit remplir pour etre acceptee par les parties prenantes. De ce point de vue, les criteres d'acceptation peuvent etre consideres comme les conditions de test qui doivent etre exercees par les tests. Les criteres d'acceptation sont generalement le resultat de la Conversation (voir section 4.5.1).

Les criteres d'acceptation sont utilises pour :

  • Definir la portee de la user story
  • Atteindre un consensus entre les parties prenantes
  • Decrire les scenarios positifs et negatifs
  • Servir de base pour les tests d'acceptation de la user story (voir section 4.5.3)
  • Permettre une planification et une estimation precises

Il existe plusieurs facons de rediger des criteres d'acceptation pour une user story. Les deux formats les plus courants sont :

  • Oriente scenario (par exemple, le format Given/When/Then utilise en BDD, voir section 2.1.3)
  • Oriente regles (par exemple, une liste de verification a puces, ou une forme tabulee de correspondance entree-sortie)

La plupart des criteres d'acceptation peuvent etre documentes dans l'un de ces deux formats. Cependant, l'equipe peut utiliser un autre format personnalise, tant que les criteres d'acceptation sont bien definis et non ambigus.

4.5.3. Developpement pilote par les tests d'acceptation (ATDD)

L'ATDD est une approche "test en premier" (voir section 2.1.3). Les cas de test sont crees avant l'implementation de la user story. Les cas de test sont crees par des membres de l'equipe ayant differentes perspectives, par exemple des clients, des developpeurs et des testeurs (Adzic 2009). Les cas de test peuvent etre executes manuellement ou automatises.

La premiere etape est un atelier de specification ou la user story et (si ce n'est pas encore fait) ses criteres d'acceptation sont analyses, discutes et rediges par les membres de l'equipe. Les incompletudes, ambiguites ou defauts de la user story sont resolus au cours de ce processus. L'etape suivante consiste a creer les cas de test. Cela peut etre fait par l'equipe dans son ensemble ou par le testeur individuellement. Les cas de test sont bases sur les criteres d'acceptation et peuvent etre vus comme des exemples du fonctionnement du logiciel. Cela aidera l'equipe a implementer correctement la user story.

Puisque les exemples et les tests sont la meme chose, ces termes sont souvent utilises de maniere interchangeable. Pendant la conception des tests, les techniques de test decrites dans les sections 4.2, 4.3 et 4.4 peuvent etre appliquees.

En general, les premiers cas de test sont positifs, confirmant le comportement correct sans exceptions ni conditions d'erreur, et comprenant la sequence d'activites executees si tout se passe comme prevu. Une fois les cas de test positifs termines, l'equipe devrait effectuer des tests negatifs. Enfin, l'equipe devrait couvrir les caracteristiques de qualite non fonctionnelles (par exemple, l'efficacite de performance, l'utilisabilite). Les cas de test doivent etre exprimes d'une maniere comprehensible pour les parties prenantes. En general, les cas de test contiennent des phrases en langage naturel impliquant les preconditions necessaires (le cas echeant), les entrees et les postconditions.

Les cas de test doivent couvrir toutes les caracteristiques de la user story et ne doivent pas aller au-dela de la story. Cependant, les criteres d'acceptation peuvent detailler certains des aspects decrits dans la user story. De plus, deux cas de test ne doivent pas decrire les memes caracteristiques de la user story.

Lorsqu'ils sont captures dans un format supporte par un framework d'automatisation des tests, les developpeurs peuvent automatiser les cas de test en ecrivant le code de support au fur et a mesure qu'ils implementent la fonctionnalite decrite par une user story. Les tests d'acceptation deviennent alors des exigences executables.

Partitions d'equivalence (EP)

  • Diviser les entrees en groupes (partitions) ou le systeme se comporte de la meme maniere
  • Partition valide : valeurs acceptees par le systeme
  • Partition invalide : valeurs rejetees par le systeme
  • Chaque valeur appartient a exactement UNE partition
  • Un seul cas de test par partition suffit (representant)
Couverture EP = partitions testees / total partitions x 100%

Exemple : champ age 18-65. Partitions : <18 (invalide), 18-65 (valide), >65 (invalide). 3 partitions au total.

Comment resoudre un exercice EP en 4 etapes
  1. Identifier la variable d'entree et ses contraintes (ex: "age entre 18 et 65")
  2. Lister les partitions : une valide (18-65), les invalides (<18, >65). S'il y a des sous-regles, creer des partitions supplementaires
  3. Choisir un representant par partition (n'importe quelle valeur dans la plage : 25 pour 18-65, 10 pour <18, 70 pour >65)
  4. Compter : couverture = partitions testees / total partitions x 100%
Exemple : D = CY - BY. Partitions : D<0 (erreur), 0<=D<18 (etudiant), 18<=D<65 (normal), D>=65 (retraite) = 4 partitions. Si 2 sont deja couvertes, il faut 2 tests supplementaires.
Piege : Lis bien les bornes ! "depasse 100$" signifie >100, pas >=100. "entre 0 et 2 inclus" signifie 0, 1 et 2 sont dans la partition.

BVA 2 valeurs (par defaut dans le syllabus)

  • Pour chaque frontiere entre 2 partitions : 2 valeurs (une de chaque cote)
  • Exemple : frontiere entre <18 et 18-65 a la valeur 18 : tester 17 et 18
  • Exemple : frontiere entre 18-65 et >65 a la valeur 65 : tester 65 et 66
  • Total : 2 frontieres x 2 valeurs = 4 valeurs limites

BVA 3 valeurs

  • Pour chaque frontiere : 3 valeurs (frontiere + 1 de chaque cote)
  • Exemple frontiere a 18 : tester 17, 18, 19
  • Exemple frontiere a 65 : tester 64, 65, 66
  • Total : 2 frontieres x 3 valeurs = 6 valeurs limites (en eliminant les doublons)
Couverture BVA = valeurs limites testees / total valeurs limites x 100%
Comment resoudre un exercice BVA en 3 etapes
  1. Identifier les frontieres entre partitions (la ou le comportement change)
  2. Pour BVA 2-valeurs : pour chaque frontiere, prendre la valeur juste en-dessous et juste au-dessus (ex: frontiere a 18 → tester 17 et 18)
  3. Pour BVA 3-valeurs : pour chaque frontiere, prendre la frontiere + 1 de chaque cote (ex: frontiere a 18 → tester 17, 18, 19)
Exemple BVA 2-val : Partitions <0, 0-2, >2. Frontieres a 0 et 2.
Frontiere 0 : tester -1 et 0. Frontiere 2 : tester 2 et 3.
Total : 4 valeurs limites = {-1, 0, 2, 3}. Si tu testes les 4 → 100% couverture BVA.
Piege : Ne confonds pas BVA 2-valeurs et 3-valeurs ! Le syllabus utilise 2-valeurs par defaut. Si la question dit "two-value BVA", c'est 2 valeurs par frontiere, pas 3.

Tables de decision

  • Conditions : les entrees/situations (lignes du haut)
  • Actions : les sorties/resultats attendus (lignes du bas)
  • Regles : chaque colonne = une combinaison unique de conditions avec ses actions
  • Nombre de regles theorique = 2^n (n = nombre de conditions booleennes)
Couverture table de decision = regles testees / total regles x 100%
Pour identifier quelle regle couvre un cas de test : verifier la combinaison de conditions et trouver la colonne correspondante.
Comment resoudre un exercice de table de decision
  1. Lire le cas de test : extraire les valeurs de chaque condition (ex: "19 ans, non inscrit, sans experience")
  2. Mapper chaque condition a la ligne correspondante de la table (Age=19-65, Inscrit=NON, Exp=0-4)
  3. Trouver la colonne ou TOUTES les conditions correspondent → c'est la regle couverte
  4. Pour la couverture : compter combien de colonnes/regles sont couvertes par l'ensemble des cas de test
Exemple : TC: homme de 66 ans, non inscrit. Dans la table : Age >65, Inscrit=NON. Chercher la colonne avec >65 et NON → c'est R4.

Transitions d'etat

  • Etat : situation dans laquelle le systeme se trouve
  • Transition : changement d'un etat a un autre
  • Evenement : ce qui declenche une transition
  • Action : ce qui resulte d'une transition
  • Garde : condition supplementaire pour qu'une transition ait lieu
Couverture transitions = transitions executees / total transitions valides x 100%
Comment resoudre un exercice de transitions d'etat
  1. Dessiner le graphe a partir de la table : etats = cercles, transitions = fleches avec evenements
  2. Lister toutes les transitions valides (compter les fleches distinctes)
  3. Tracer le chemin du cas de test en suivant les evenements un par un depuis l'etat initial
  4. Compter les transitions distinctes couvertes par le chemin
  5. Verifier la faisabilite : apres un etat final (End), plus aucune transition n'est possible !
Exemple : Sequence "Available, ChangeRoom, NotAvailable, Available, Pay"
S1→S2 (Available) → S2→S1 (ChangeRoom) → S1→S3 (NotAvailable) → S3→S2 (Available) → S2→S4 (Pay)
= 5 transitions distinctes couvertes sur 7 = 71% couverture.
Piege : Un meme evenement peut correspondre a des transitions DIFFERENTES selon l'etat de depart ! "Available" depuis S1 (→S2) n'est PAS la meme transition que "Available" depuis S3 (→S2).

Couverture des instructions

  • Chaque instruction du code executee au moins une fois
  • Mesure : instructions executees / total instructions x 100%
100% couverture instructions NE GARANTIT PAS 100% couverture branches ! Une branche "else" vide peut ne pas etre testee.

Couverture des branches

  • Chaque branche (vrai ET faux) de chaque decision executee au moins une fois
  • Mesure : branches executees / total branches x 100%
100% branches → 100% instructions (garanti) | 100% instructions ↗ 100% branches (PAS garanti)
Comment verifier la couverture d'instructions et de branches
  1. Tracer le chemin du cas de test dans le code (quelles lignes sont executees)
  2. Instructions : cocher chaque ligne executee. Couverture = lignes cochees / total lignes
  3. Branches : pour chaque IF/decision, verifier si le chemin VRAI et le chemin FAUX ont ete empruntes
  4. Rappel : 100% branches garantit 100% instructions. L'inverse est FAUX.
Piege : Un IF sans ELSE a quand meme 2 branches (vrai et faux). Si tu ne testes que le cas vrai, tu as 100% instructions mais seulement 50% branches.

Error guessing (Supposition d'erreurs)

  • Le testeur utilise son experience pour anticiper les erreurs, defauts et defaillances
  • Base sur : defauts passes, erreurs typiques des developpeurs, types de defaillances connues
  • Cree des "listes de bugs" ou "attaques" (taxonomies de defauts)
Error guessing n'anticipe PAS les causes racines ! Il anticipe les erreurs, defauts et defaillances.

Test exploratoire

  • Conception, execution et evaluation des tests simultanement
  • Utilise des chartes de test (session-based)
  • Peut utiliser des techniques boite noire pendant l'exploration
  • Ideal quand les specifications sont limitees ou le temps est court
Le test exploratoire ne permet PAS de predire de maniere fiable le nombre de defauts restants (pas de metriques de couverture formelles).

Test base sur des checklists

Le testeur utilise une liste de conditions a verifier. Les checklists sont construites a partir de l'experience, des standards, ou des defauts connus. La couverture peut etre imprecise car les items sont souvent a un niveau d'abstraction eleve.

User stories : Card, Conversation, Confirmation

  • Card : Support physique ou numerique decrivant la user story
  • Conversation : Echanges entre equipe pour clarifier les details
  • Confirmation : Criteres d'acceptation utilises pour confirmer que la story est complete

Collaboration pour comprendre ce qui doit etre livre : les user stories sont creees ENSEMBLE par representants metier, developpeurs et testeurs.

Criteres d'acceptation : INVEST et Given/When/Then

  • INVEST : Independent, Negotiable, Valuable, Estimable, Small, Testable
  • Given/When/Then : Given [contexte initial], When [action], Then [resultat attendu]
