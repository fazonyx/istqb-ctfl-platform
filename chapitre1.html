1.1. Qu'est-ce que le test ?

Objectifs d'apprentissage :
FL-1.1.1 (K1) Identifier les objectifs de test typiques
FL-1.1.2 (K2) Differencier le test du debogage

Les systemes logiciels font partie integrante de notre vie quotidienne. La plupart des gens ont deja eu l'experience d'un logiciel qui ne fonctionnait pas comme prevu. Un logiciel qui ne fonctionne pas correctement peut entrainer de nombreux problemes, notamment des pertes d'argent, de temps ou de reputation commerciale, et, dans les cas extremes, meme des blessures ou la mort. Le test logiciel evalue la qualite du logiciel et aide a reduire le risque de defaillance du logiciel en exploitation.

Le test logiciel est un ensemble d'activites visant a decouvrir des defauts et a evaluer la qualite des produits d'activite logiciels. Ces produits d'activite, lorsqu'ils sont testes, sont appeles objets de test. Une idee fausse courante sur le test est qu'il consiste uniquement a executer des tests (c'est-a-dire executer le logiciel et verifier les resultats des tests). Cependant, le test logiciel comprend egalement d'autres activites et doit etre aligne sur le cycle de vie du developpement logiciel (voir chapitre 2).

Une autre idee fausse courante sur le test est qu'il se concentre entierement sur la verification de l'objet de test. Bien que le test implique la verification, c'est-a-dire verifier si le systeme repond aux exigences specifiees, il implique egalement la validation, qui consiste a verifier si le systeme repond aux besoins des utilisateurs et des autres parties prenantes dans son environnement operationnel.

Le test peut etre dynamique ou statique. Le test dynamique implique l'execution du logiciel, tandis que le test statique ne l'implique pas. Le test statique comprend les revues (voir chapitre 3) et l'analyse statique. Le test dynamique utilise differents types de techniques de test et d'approches de test pour deriver des cas de test (voir chapitre 4).

Le test n'est pas seulement une activite technique. Il doit egalement etre correctement planifie, gere, estime, surveille et controle (voir chapitre 5).

Les testeurs utilisent des outils (voir chapitre 6), mais il est important de rappeler que le test est en grande partie une activite intellectuelle, exigeant des testeurs qu'ils possedent des connaissances specialisees, utilisent des competences analytiques et appliquent la pensee critique et la pensee systemique (Myers 2011, Roman 2018).

La norme ISO/IEC/IEEE 29119-1 fournit des informations complementaires sur les concepts du test logiciel.

1.1.1. Objectifs du test

Les objectifs de test typiques sont :

  • Evaluer les produits d'activite tels que les exigences, les user stories, les conceptions et le code
  • Provoquer des defaillances et trouver des defauts
  • Assurer la couverture requise d'un objet de test
  • Reduire le niveau de risque d'une qualite logicielle inadequate
  • Verifier si les exigences specifiees ont ete satisfaites
  • Verifier qu'un objet de test est conforme aux exigences contractuelles, legales et reglementaires
  • Fournir des informations aux parties prenantes pour leur permettre de prendre des decisions eclairees
  • Renforcer la confiance dans la qualite de l'objet de test
  • Valider si l'objet de test est complet et fonctionne comme attendu par les parties prenantes

Les objectifs de test peuvent varier en fonction du contexte, qui inclut le produit d'activite teste, le niveau de test, les risques, le cycle de vie du developpement logiciel (SDLC) suivi, et des facteurs lies au contexte metier, par exemple la structure de l'entreprise, les considerations concurrentielles ou le delai de mise sur le marche.

1.1.2. Test et debogage

Le test et le debogage sont des activites distinctes. Le test peut declencher des defaillances causees par des defauts dans le logiciel (test dynamique) ou peut directement trouver des defauts dans l'objet de test (test statique).

Lorsque le test dynamique (voir chapitre 4) declenche une defaillance, le debogage consiste a trouver les causes de cette defaillance (defauts), a analyser ces causes et a les eliminer. Le processus typique de debogage dans ce cas comprend :

  • Reproduction d'une defaillance
  • Diagnostic (trouver le defaut)
  • Correction du defaut

Le test de confirmation subsequent verifie si les corrections ont resolu le probleme. De preference, le test de confirmation est effectue par la meme personne qui a realise le test initial. Un test de regression subsequent peut egalement etre effectue pour verifier si les corrections ne causent pas de defaillances dans d'autres parties de l'objet de test (voir section 2.2.3 pour plus d'informations sur le test de confirmation et le test de regression).

Lorsque le test statique identifie un defaut, le debogage consiste a le supprimer. Il n'y a pas besoin de reproduction ni de diagnostic, puisque le test statique trouve directement les defauts et ne peut pas provoquer de defaillances (voir chapitre 3).

1.2. Pourquoi le test est-il necessaire ?

Objectifs d'apprentissage :
FL-1.2.1 (K2) Illustrer pourquoi le test est necessaire
FL-1.2.2 (K1) Rappeler la relation entre le test et l'assurance qualite
FL-1.2.3 (K2) Distinguer cause racine, erreur, defaut et defaillance

Le test, en tant que forme de controle qualite, aide a atteindre les objectifs de test convenus dans le cadre des contraintes definies de portee, de temps, de qualite et de budget. La contribution du test au succes ne devrait pas se limiter aux activites de l'equipe de test. Toute partie prenante peut utiliser ses competences en test pour rapprocher le projet du succes. Tester les composants, les systemes et les produits d'activite associes (par exemple, la documentation) aide a identifier les defauts dans le logiciel.

1.2.1. Contributions du test au succes

Le test fournit un moyen rentable de detecter les defauts. Ces defauts peuvent ensuite etre supprimes (par le debogage - une activite hors test), de sorte que le test contribue indirectement a des objets de test de meilleure qualite.

Le test fournit un moyen d'evaluer directement la qualite d'un objet de test a differentes phases du SDLC. Ces mesures sont utilisees dans le cadre d'une activite plus large de gestion de projet, contribuant aux decisions de passage a la phase suivante du SDLC, comme la decision de mise en production.

Le test offre aux utilisateurs une representation indirecte dans le projet de developpement. Les testeurs s'assurent que leur comprehension des besoins des utilisateurs est prise en compte tout au long du cycle de vie du developpement. L'alternative serait d'impliquer un ensemble representatif d'utilisateurs dans le projet de developpement, ce qui n'est generalement pas possible en raison des couts eleves et du manque de disponibilite d'utilisateurs adequats.

Le test peut egalement etre requis pour satisfaire des exigences contractuelles ou legales, ou pour se conformer a des normes reglementaires.

1.2.2. Test et assurance qualite (QA)

Bien que les termes "test" et "assurance qualite" (QA) soient souvent utilises de maniere interchangeable, le test et la QA ne sont pas la meme chose.

Le test est une approche corrective orientee produit qui se concentre sur les activites soutenant l'atteinte de niveaux de qualite appropries. Le test est une forme majeure de controle qualite, tandis que d'autres incluent les methodes formelles (verification de modele et preuve de correction), la simulation et le prototypage.

La QA est une approche preventive orientee processus qui se concentre sur la mise en oeuvre et l'amelioration des processus. Elle repose sur le principe que si un bon processus est suivi correctement, il produira un bon produit. La QA s'applique a la fois aux processus de developpement et de test, et releve de la responsabilite de chacun dans un projet.

Les resultats de test sont utilises par la QA et le test. Dans le test, ils servent a corriger les defauts, tandis que dans la QA, ils fournissent un retour sur la performance des processus de developpement et de test.

1.2.3. Erreurs, defauts, defaillances et causes racines

Les etres humains commettent des erreurs, qui produisent des defauts (anomalies, bugs), qui a leur tour peuvent entrainer des defaillances. Les humains commettent des erreurs pour diverses raisons, telles que la pression du temps, la complexite des produits d'activite, des processus, de l'infrastructure ou des interactions, ou simplement parce qu'ils sont fatigues ou manquent de formation adequate.

Les defauts peuvent etre trouves dans la documentation, comme une specification d'exigences ou un script de test, dans le code source, ou dans un produit d'activite de support tel qu'un fichier de build. Les defauts dans les produits d'activite produits plus tot dans le SDLC, s'ils ne sont pas detectes, menent souvent a des produits d'activite defectueux plus tard dans le cycle de vie. Si un defaut dans le code est execute, le systeme peut ne pas faire ce qu'il devrait faire, ou faire quelque chose qu'il ne devrait pas, provoquant une defaillance. Certains defauts entraineront toujours une defaillance s'ils sont executes, tandis que d'autres n'entraineront une defaillance que dans des circonstances specifiques, et certains ne provoqueront jamais de defaillance.

Les erreurs et les defauts ne sont pas la seule cause des defaillances. Les defaillances peuvent egalement etre causees par des conditions environnementales, comme lorsque des radiations ou des champs electromagnetiques provoquent des defauts dans le firmware.

Une cause racine est une raison fondamentale de l'apparition d'un probleme (par exemple, une situation qui conduit a une erreur). Les causes racines sont identifiees par l'analyse des causes racines, qui est generalement effectuee lorsqu'une defaillance survient ou qu'un defaut est identifie. On considere que des defaillances ou defauts similaires peuvent etre evites ou leur frequence reduite en traitant la cause racine, par exemple en la supprimant.

1.3. Principes du test

Objectifs d'apprentissage :
FL-1.3.1 (K2) Expliquer les sept principes du test

Un certain nombre de principes de test offrant des lignes directrices generales applicables a tous les tests ont ete proposes au fil des annees. Ce syllabus decrit sept de ces principes.

1. Le test montre la presence de defauts, pas leur absence. Le test peut montrer que des defauts sont presents dans l'objet de test, mais ne peut pas prouver qu'il n'y en a pas (Buxton 1970). Le test reduit la probabilite que des defauts restent non decouverts dans l'objet de test, mais meme si aucun defaut n'est trouve, le test ne peut pas prouver la correction de l'objet de test.

2. Le test exhaustif est impossible. Tout tester n'est pas realisable sauf dans les cas triviaux (Manna 1978). Plutot que de tenter de tester de maniere exhaustive, les techniques de test (voir chapitre 4), la priorisation des cas de test (voir section 5.1.5) et le test base sur les risques (voir section 5.2) devraient etre utilises pour concentrer les efforts de test.

3. Tester tot permet d'economiser du temps et de l'argent. Les defauts supprimes tot dans le processus ne causeront pas de defauts subsequents dans les produits d'activite derives. Le cout de la qualite sera reduit car moins de defaillances surviendront plus tard dans le SDLC (Boehm 1981). Pour trouver les defauts tot, le test statique (voir chapitre 3) et le test dynamique (voir chapitre 4) devraient etre commences le plus tot possible.

4. Les defauts se regroupent. Un petit nombre de composants du systeme contient generalement la plupart des defauts decouverts ou est responsable de la plupart des defaillances operationnelles (Enders 1975). Ce phenomene est une illustration du principe de Pareto. Les regroupements de defauts prevus, et les regroupements de defauts reels observes pendant le test ou en exploitation, constituent une donnee importante pour le test base sur les risques (voir section 5.2).

5. Les tests s'usent. Si les memes tests sont repetes de nombreuses fois, ils deviennent de moins en moins efficaces pour detecter de nouveaux defauts (Beizer 1990). Pour surmonter cet effet, les tests existants et les donnees de test peuvent avoir besoin d'etre modifies, et de nouveaux tests peuvent devoir etre ecrits. Cependant, dans certains cas, repeter les memes tests peut avoir un resultat benefique, par exemple dans le test de regression automatise (voir section 2.2.3).

6. Le test depend du contexte. Il n'existe pas d'approche unique universellement applicable au test. Le test est realise differemment selon les contextes (Kaner 2011).

7. L'illusion de l'absence de defauts. C'est une illusion (c'est-a-dire une idee fausse) de s'attendre a ce que la verification du logiciel garantisse le succes d'un systeme. Tester minutieusement toutes les exigences specifiees et corriger tous les defauts trouves pourrait quand meme produire un systeme qui ne repond pas aux besoins et aux attentes des utilisateurs, qui n'aide pas a atteindre les objectifs metier du client, et qui est inferieur par rapport a d'autres systemes concurrents. En plus de la verification, la validation devrait egalement etre effectuee (Boehm 1981).

1.4. Activites de test, testware et roles de test

Le test depend du contexte, mais, a un niveau eleve, il existe des ensembles communs d'activites de test sans lesquels le test a moins de chances d'atteindre ses objectifs. Ces ensembles d'activites de test forment un processus de test. Le processus de test peut etre adapte a une situation donnee en fonction de divers facteurs. Les activites de test incluses dans ce processus, la maniere dont elles sont mises en oeuvre et le moment ou elles se produisent sont normalement decides dans le cadre de la planification des tests pour la situation specifique (voir section 5.1).

Les sections suivantes decrivent les aspects generaux de ce processus de test en termes d'activites et de taches de test, d'impact du contexte, de testware, de tracabilite entre la base de test et le testware, et de roles de test. La norme ISO/IEC/IEEE 29119-2 fournit des informations complementaires sur les processus de test.

1.4.1. Activites et taches de test

Un processus de test se compose generalement des principaux groupes d'activites decrits ci-dessous. Bien que beaucoup de ces activites semblent suivre une sequence logique, elles sont souvent mises en oeuvre de maniere iterative ou en parallele. Ces activites de test doivent generalement etre adaptees au systeme et au projet.

La planification des tests consiste a definir les objectifs de test puis a selectionner une approche qui atteint au mieux les objectifs dans les contraintes imposees par le contexte global. La planification des tests est expliquee plus en detail dans la section 5.1.

Le pilotage et le controle des tests. Le pilotage des tests implique la verification continue de toutes les activites de test et la comparaison de l'avancement reel par rapport au plan. Le controle des tests implique de prendre les mesures necessaires pour atteindre les objectifs de test. Le pilotage et le controle des tests sont expliques plus en detail dans la section 5.3.

L'analyse de test comprend l'analyse de la base de test pour identifier les fonctionnalites testables. Les conditions de test associees sont definies et priorisees, en tenant compte des risques et des niveaux de risque associes (voir section 5.2). La base de test et l'objet de test sont egalement evalues pour identifier les defauts qu'ils peuvent contenir et pour evaluer leur testabilite. L'analyse de test est souvent soutenue par l'utilisation de techniques de test (voir chapitre 4). L'analyse de test repond a la question "que tester ?" en termes de criteres de couverture mesurables.

La conception des tests comprend l'elaboration des conditions de test en cas de test et autres testware (par exemple, les chartes de test). Cette activite implique souvent l'identification des elements de couverture, qui servent de guide pour specifier les entrees des cas de test. Les techniques de test (voir chapitre 4) peuvent etre utilisees pour soutenir cette activite. La conception des tests comprend egalement la definition des exigences en matiere de donnees de test, la conception de l'environnement de test et l'identification de l'infrastructure et des outils necessaires. La conception des tests repond a la question "comment tester ?".

L'implementation des tests comprend la creation ou l'acquisition du testware necessaire a l'execution des tests (par exemple, les donnees de test). Les cas de test peuvent etre organises en procedures de test, qui sont souvent assemblees en suites de test. Des scripts de test manuels et automatises sont crees. Les procedures de test sont priorisees et organisees dans un calendrier d'execution des tests pour une execution efficace (voir section 5.1.5). L'environnement de test est construit et verifie pour s'assurer qu'il est correctement configure.

L'execution des tests comprend l'execution des tests conformement au calendrier d'execution des tests (series de tests). L'execution des tests peut etre manuelle ou automatisee. L'execution des tests peut prendre de nombreuses formes, y compris le test continu ou les sessions de test en binome. Les resultats de test reels sont compares aux resultats attendus. Les resultats des tests sont enregistres. Les anomalies sont analysees pour identifier leurs causes probables. Cette analyse permet de signaler les anomalies sur la base des defaillances observees (voir section 5.5).

La cloture des tests survient generalement aux jalons du projet (par exemple, mise en production, fin d'iteration, achevement d'un niveau de test). Pour tout defaut non resolu, des demandes de changement ou des elements du backlog produit sont crees. Tout testware pouvant etre utile a l'avenir est identifie et archive ou transmis aux equipes appropriees. L'environnement de test est arrete dans un etat convenu. Les activites de test sont analysees pour identifier les lecons apprises et les ameliorations pour les futures iterations, versions ou projets (voir section 2.1.6). Un rapport de cloture des tests est cree et communique aux parties prenantes.

1.4.2. Processus de test en contexte

Le test n'est pas realise de maniere isolee. Les activites de test font partie integrante des processus de developpement menes au sein d'une organisation. Le test est egalement finance par les parties prenantes et son objectif final est d'aider a satisfaire les besoins metier des parties prenantes. Par consequent, la maniere dont le test est effectue dependra d'un certain nombre de facteurs contextuels, notamment :

  • Les parties prenantes (besoins, attentes, exigences, volonte de cooperer, etc.)
  • Les membres de l'equipe (competences, connaissances, niveau d'experience, disponibilite, besoins en formation, etc.)
  • Le domaine metier (criticite de l'objet de test, risques identifies, besoins du marche, reglementations legales specifiques, etc.)
  • Les facteurs techniques (type de logiciel, architecture du produit, technologie utilisee, etc.)
  • Les contraintes du projet (portee, temps, budget, ressources, etc.)
  • Les facteurs organisationnels (structure organisationnelle, politiques existantes, pratiques utilisees, etc.)
  • Le cycle de vie du developpement logiciel (pratiques d'ingenierie, methodes de developpement, etc.)
  • Les outils (disponibilite, utilisabilite, conformite, etc.)

Ces facteurs auront un impact sur de nombreuses questions liees au test, notamment : la strategie de test, les techniques de test utilisees, le degre d'automatisation des tests, le niveau de couverture requis, le niveau de detail du testware, le reporting de test, etc.

1.4.3. Testware

Le testware est cree comme produits d'activite resultant des activites de test decrites dans la section 1.4.1. Il existe une variation significative dans la maniere dont les differentes organisations produisent, faconnent, nomment, organisent et gerent leurs produits d'activite. Une gestion de configuration appropriee (voir section 5.4) assure la coherence et l'integrite des produits d'activite. La liste suivante de produits d'activite n'est pas exhaustive :

  • Produits d'activite de la planification des tests : plan de test, calendrier de test, registre des risques, criteres d'entree et criteres de sortie (voir section 5.1). Le registre des risques est une liste de risques avec la probabilite du risque, l'impact du risque et les informations sur l'attenuation des risques (voir section 5.2). Le calendrier de test, le registre des risques, les criteres d'entree et de sortie font souvent partie du plan de test.
  • Produits d'activite du pilotage et du controle des tests : rapports d'avancement des tests (voir section 5.3.2), documentation des directives de controle (voir section 5.3) et informations sur les risques (voir section 5.2).
  • Produits d'activite de l'analyse de test : conditions de test (priorisees) (par exemple, criteres d'acceptation, voir section 4.5.2), et rapports de defauts concernant les defauts dans la base de test (s'ils ne sont pas corriges directement).
  • Produits d'activite de la conception des tests : cas de test (priorises), chartes de test, elements de couverture, exigences en matiere de donnees de test et exigences en matiere d'environnement de test.
  • Produits d'activite de l'implementation des tests : procedures de test, scripts de test manuels et automatises, suites de test, donnees de test, calendrier d'execution des tests et elements de l'environnement de test. Les exemples d'elements de l'environnement de test comprennent : les bouchons (stubs), les pilotes (drivers), les simulateurs et les virtualisations de services.
  • Produits d'activite de l'execution des tests : journaux de test et rapports de defauts (voir section 5.5).
  • Produits d'activite de la cloture des tests : rapport de cloture des tests (voir section 5.3.2), actions d'amelioration pour les projets ou iterations suivants, lecons apprises documentees et demandes de changement (par exemple, en tant qu'elements du backlog produit).

1.4.4. Tracabilite entre la base de test et le testware

Pour mettre en oeuvre un pilotage et un controle efficaces des tests, il est important d'etablir et de maintenir la tracabilite tout au long du processus de test entre les elements de la base de test, le testware associe a ces elements (par exemple, les conditions de test, les risques, les cas de test), les resultats de test et les defauts.

Une tracabilite precise soutient l'evaluation de la couverture, il est donc tres utile que des criteres de couverture mesurables soient definis dans la base de test. Les criteres de couverture peuvent fonctionner comme des indicateurs cles de performance pour guider les activites qui montrent dans quelle mesure les objectifs de test ont ete atteints (voir section 1.1.1). Par exemple :

  • La tracabilite des cas de test vers les exigences peut verifier que les exigences sont couvertes par des cas de test.
  • La tracabilite des resultats de test vers les risques peut etre utilisee pour evaluer le niveau de risque residuel dans un objet de test.

En plus de l'evaluation de la couverture, une bonne tracabilite permet de determiner l'impact des changements, facilite les audits et aide a satisfaire les criteres de gouvernance informatique. Une bonne tracabilite rend egalement les rapports d'avancement et de cloture des tests plus facilement comprehensibles en incluant le statut des elements de la base de test. Cela peut egalement aider a communiquer les aspects techniques du test aux parties prenantes de maniere comprehensible. La tracabilite fournit des informations pour evaluer la qualite du produit, la capacite du processus et l'avancement du projet par rapport aux objectifs metier.

1.4.5. Roles dans le test

Dans ce syllabus, deux roles principaux dans le test sont couverts : un role de gestion des tests et un role de test. Les activites et taches assignees a ces deux roles dependent de facteurs tels que le contexte du projet et du produit, les competences des personnes dans ces roles et l'organisation.

Le role de gestion des tests assume la responsabilite globale du processus de test, de l'equipe de test et de la direction des activites de test. Le role de gestion des tests est principalement axe sur les activites de planification des tests, de pilotage des tests, de controle des tests et de cloture des tests. La maniere dont le role de gestion des tests est exerce varie en fonction du contexte. Par exemple, dans le developpement logiciel Agile, certaines taches de gestion des tests peuvent etre prises en charge par l'equipe Agile. Les taches couvrant plusieurs equipes ou l'ensemble de l'organisation peuvent etre effectuees par des responsables de test en dehors de l'equipe de developpement.

Le role de test assume la responsabilite globale de l'aspect ingenierie (technique) du test. Le role de test est principalement axe sur les activites d'analyse de test, de conception des tests, d'implementation des tests et d'execution des tests.

Differentes personnes peuvent assumer ces roles a differents moments. Par exemple, le role de gestion des tests peut etre exerce par un chef d'equipe, un responsable de test, un responsable de developpement, etc. Il est egalement possible qu'une seule personne assume les roles de test et de gestion des tests en meme temps.

1.5. Competences essentielles et bonnes pratiques en test

Objectifs d'apprentissage :
FL-1.5.1 (K2) Donner des exemples de competences generiques requises pour le test
FL-1.5.2 (K1) Rappeler les avantages de l'approche equipe entiere
FL-1.5.3 (K2) Distinguer les avantages et inconvenients de l'independance du test

La competence est la capacite a bien faire quelque chose qui provient des connaissances, de la pratique et de l'aptitude. Les bons testeurs doivent posseder certaines competences essentielles pour bien faire leur travail. Les bons testeurs doivent etre des membres d'equipe efficaces et doivent etre capables d'effectuer des tests a differents niveaux d'independance du test.

1.5.1. Competences generiques requises pour le test

Bien qu'etant generiques, les competences suivantes sont particulierement pertinentes pour les testeurs :

  • Connaissances en test (pour augmenter l'efficacite du test, par exemple en utilisant des techniques de test)
  • Rigueur, minutie, curiosite, attention aux details, methodisme (pour identifier les defauts, en particulier ceux qui sont difficiles a trouver)
  • Bonnes competences en communication, ecoute active, esprit d'equipe (pour interagir efficacement avec toutes les parties prenantes, transmettre des informations aux autres, etre compris, et signaler et discuter des defauts)
  • Pensee analytique, pensee critique, creativite (pour augmenter l'efficacite du test)
  • Connaissances techniques (pour augmenter l'efficience du test, par exemple en utilisant des outils de test appropries)
  • Connaissance du domaine (pour etre capable de comprendre et de communiquer avec les utilisateurs finaux/representants metier)

Les testeurs sont souvent porteurs de mauvaises nouvelles. C'est un trait humain courant de blamer le porteur de mauvaises nouvelles. Cela rend les competences en communication cruciales pour les testeurs. La communication des resultats de test peut etre percue comme une critique du produit et de son auteur. Le biais de confirmation peut rendre difficile l'acceptation d'informations qui contredisent les croyances actuelles. Certaines personnes peuvent percevoir le test comme une activite destructrice, meme s'il contribue grandement au succes du projet et a la qualite du produit. Pour tenter d'ameliorer cette perception, les informations sur les defauts et les defaillances devraient etre communiquees de maniere constructive.

1.5.2. Approche equipe entiere

L'une des competences importantes pour un testeur est la capacite a travailler efficacement dans un contexte d'equipe et a contribuer positivement aux objectifs de l'equipe. L'approche equipe entiere - une pratique issue de l'Extreme Programming (voir section 2.1) - s'appuie sur cette competence.

Dans l'approche equipe entiere, tout membre de l'equipe possedant les connaissances et competences necessaires peut effectuer n'importe quelle tache, et chacun est responsable de la qualite. Les membres de l'equipe partagent le meme espace de travail (physique ou virtuel), car la co-localisation facilite la communication et l'interaction. L'approche equipe entiere ameliore la dynamique d'equipe, renforce la communication et la collaboration au sein de l'equipe, et cree une synergie en permettant aux differents ensembles de competences au sein de l'equipe d'etre exploites au benefice du projet.

Les testeurs travaillent en etroite collaboration avec les autres membres de l'equipe pour s'assurer que les niveaux de qualite souhaites sont atteints. Cela comprend la collaboration avec les representants metier pour les aider a creer des tests d'acceptation adaptes et le travail avec les developpeurs pour convenir de la strategie de test et decider des approches d'automatisation des tests. Les testeurs peuvent ainsi transferer leurs connaissances en test aux autres membres de l'equipe et influencer le developpement du produit.

Selon le contexte, l'approche equipe entiere peut ne pas toujours etre appropriee. Par exemple, dans certaines situations, comme les systemes critiques pour la securite, un niveau eleve d'independance du test peut etre necessaire.

1.5.3. Independance du test

Un certain degre d'independance rend le testeur plus efficace dans la detection des defauts en raison des differences entre les biais cognitifs de l'auteur et ceux du testeur (cf. Salman 1995). L'independance ne remplace cependant pas la familiarite, par exemple les developpeurs peuvent efficacement trouver de nombreux defauts dans leur propre code.

Les produits d'activite peuvent etre testes par leur auteur (pas d'independance), par les pairs de l'auteur de la meme equipe (une certaine independance), par des testeurs exterieurs a l'equipe de l'auteur mais au sein de l'organisation (independance elevee), ou par des testeurs exterieurs a l'organisation (independance tres elevee). Pour la plupart des projets, il est generalement preferable d'effectuer les tests avec plusieurs niveaux d'independance (par exemple, les developpeurs effectuant les tests de composants et les tests d'integration de composants, l'equipe de test effectuant les tests systeme et les tests d'integration systeme, et les representants metier effectuant les tests d'acceptation).

Le principal avantage de l'independance du test est que les testeurs independants sont susceptibles de reconnaitre differents types de defaillances et de defauts par rapport aux developpeurs en raison de leurs parcours, perspectives techniques et biais differents. De plus, un testeur independant peut verifier, remettre en question ou refuter les hypotheses formulees par les parties prenantes lors de la specification et de l'implementation du systeme.

Cependant, il existe egalement certains inconvenients. Les testeurs independants peuvent etre isoles de l'equipe de developpement, ce qui peut entrainer un manque de collaboration, des problemes de communication ou une relation conflictuelle avec l'equipe de developpement. Les developpeurs peuvent perdre le sens de leur responsabilite en matiere de qualite. Les testeurs independants peuvent etre percus comme un goulot d'etranglement ou etre blames pour les retards de mise en production.

Pourquoi le test est necessaire

Le test est necessaire pour detecter les defauts, reduire les risques de defaillances en production, satisfaire les exigences contractuelles et reglementaires, et contribuer au succes du projet.

Les 7 objectifs du test

  • Evaluer les produits d'activite (exigences, user stories, conception, code)
  • Detecter les defaillances et les defauts
  • Assurer la couverture requise d'un objet de test
  • Reduire le niveau de risque d'un logiciel de qualite insuffisante
  • Verifier si les exigences specifiees sont satisfaites
  • Verifier la conformite aux exigences contractuelles, legales et reglementaires
  • Fournir des informations aux parties prenantes pour prise de decision eclairee
Attention : "Corriger les defauts" n'est PAS un objectif du test. Corriger = debogage (activite du developpeur).

Test vs QA vs Debogage

  • Test : Activite orientee produit, vise a detecter les defauts et evaluer la qualite
  • QA (Assurance Qualite) : Activite orientee processus, vise a ameliorer les processus pour prevenir les defauts
  • Debogage : Activite du developpeur, consiste a trouver, analyser et supprimer la cause d'une defaillance

Chaine causale : Erreur - Defaut - Defaillance

  • Cause racine : Raison fondamentale (fatigue, pression, manque de formation...)
  • Erreur : Action humaine produisant un resultat incorrect
  • Defaut (bug) : Imperfection dans un produit d'activite (code, document...)
  • Defaillance : Evenement ou le systeme ne fait pas ce qu'il devrait
Un defaut n'entraine pas toujours une defaillance. Une defaillance peut aussi venir de l'environnement (radiation, pollution).
Comment identifier erreur/defaut/defaillance dans un scenario d'examen
  1. Reperer l'action humaine incorrecte → c'est l'erreur
  2. Reperer le produit d'activite impacte (code, doc, spec) → le defaut est LA-DEDANS
  3. Reperer le comportement observable incorrect du systeme en execution → c'est la defaillance
  4. Chercher le pourquoi profond de l'erreur humaine (fatigue, pression...) → c'est la cause racine
Exemple : Un dev fatigue (cause racine) ecrit ">" au lieu de ">=" (erreur). Le code contient la mauvaise condition (defaut). Le systeme refuse 18 ans alors qu'il devrait accepter (defaillance).
Piege courant : L'amende recue par l'entreprise n'est PAS une defaillance du systeme — c'est une consequence. La defaillance c'est le comportement incorrect du logiciel.

Les 7 principes du test

#PrincipeExplication
1Le test montre la presence de defauts, pas leur absenceLe test peut montrer qu'il y a des defauts, mais ne peut pas prouver qu'il n'y en a pas.
2Le test exhaustif est impossibleTester toutes les combinaisons est impossible sauf pour les cas triviaux. Il faut prioriser (risques, techniques).
3Tester tot economise temps et argentLes defauts trouves tot coutent moins cher a corriger (shift-left).
4Les defauts se regroupentUn petit nombre de composants contient la majorite des defauts (principe de Pareto).
5L'usure des tests (Pesticide paradox)Repeter les memes tests finit par ne plus trouver de nouveaux defauts. Il faut varier les tests.
6Le test depend du contexteL'approche de test varie selon le contexte (e-commerce vs medical vs embarque).
7L'illusion de l'absence de defautsUn logiciel sans bug peut quand meme ne pas satisfaire les besoins des utilisateurs.
Comment choisir le bon principe dans une question d'examen
  1. La question parle de repeter les memes tests sans trouver de nouveaux defauts → Usure des tests (paradoxe du pesticide)
  2. La question parle d'un systeme sans bug mais qui ne satisfait pas les utilisateurs → Absence-of-defects fallacy
  3. La question parle de prioriser les tests car tout tester est impossible → Test exhaustif impossible
  4. La question parle de trouver plus de defauts dans certains modules → Regroupement des defauts (Pareto)
  5. La question mentionne tester tot, shift-left, cout de correction → Tester tot
  6. La question compare des approches differentes selon le domaine (medical vs jeu) → Contexte
Piege : "Tests wear out" et "Absence-of-defects" sont les 2 principes les plus confondus. Wear out = les TESTS s'usent (il faut varier). Absence = le PRODUIT sans bug peut etre inutile (il faut valider les besoins).

Testware

Produits d'activite crees pendant le processus de test : plan de test, cas de test, donnees de test, procedures de test, scripts automatises, resultats, rapports de defauts, chartes de test exploratoire.

Tracabilite

La tracabilite relie les elements de base de test aux cas de test et resultats. Elle permet : evaluer la couverture, l'analyse d'impact des changements (selectionner les tests de regression), la conformite aux audits, et des rapports comprehensibles.

Competences essentielles du testeur

  • Connaissance du domaine metier
  • Competences techniques (outils, automatisation)
  • Pensee critique et analytique
  • Bon joueur d'equipe, communication
  • Attention aux details

Approche equipe entiere (Whole Team)

Tout membre de l'equipe peut effectuer des taches liees au test. Les testeurs collaborent avec les developpeurs ET les representants metier. Le testeur aide les representants metier a creer des tests d'acceptation adaptes. La qualite est la responsabilite de toute l'equipe.
