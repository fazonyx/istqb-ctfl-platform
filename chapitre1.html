Pourquoi le test est necessaire

Le test est necessaire pour detecter les defauts, reduire les risques de defaillances en production, satisfaire les exigences contractuelles et reglementaires, et contribuer au succes du projet.

Les 7 objectifs du test

  • Evaluer les produits d'activite (exigences, user stories, conception, code)
  • Detecter les defaillances et les defauts
  • Assurer la couverture requise d'un objet de test
  • Reduire le niveau de risque d'un logiciel de qualite insuffisante
  • Verifier si les exigences specifiees sont satisfaites
  • Verifier la conformite aux exigences contractuelles, legales et reglementaires
  • Fournir des informations aux parties prenantes pour prise de decision eclairee
Attention : "Corriger les defauts" n'est PAS un objectif du test. Corriger = debogage (activite du developpeur).

Test vs QA vs Debogage

  • Test : Activite orientee produit, vise a detecter les defauts et evaluer la qualite
  • QA (Assurance Qualite) : Activite orientee processus, vise a ameliorer les processus pour prevenir les defauts
  • Debogage : Activite du developpeur, consiste a trouver, analyser et supprimer la cause d'une defaillance

Chaine causale : Erreur - Defaut - Defaillance

  • Cause racine : Raison fondamentale (fatigue, pression, manque de formation...)
  • Erreur : Action humaine produisant un resultat incorrect
  • Defaut (bug) : Imperfection dans un produit d'activite (code, document...)
  • Defaillance : Evenement ou le systeme ne fait pas ce qu'il devrait
Un defaut n'entraine pas toujours une defaillance. Une defaillance peut aussi venir de l'environnement (radiation, pollution).
Comment identifier erreur/defaut/defaillance dans un scenario d'examen
  1. Reperer l'action humaine incorrecte → c'est l'erreur
  2. Reperer le produit d'activite impacte (code, doc, spec) → le defaut est LA-DEDANS
  3. Reperer le comportement observable incorrect du systeme en execution → c'est la defaillance
  4. Chercher le pourquoi profond de l'erreur humaine (fatigue, pression...) → c'est la cause racine
Exemple : Un dev fatigue (cause racine) ecrit ">" au lieu de ">=" (erreur). Le code contient la mauvaise condition (defaut). Le systeme refuse 18 ans alors qu'il devrait accepter (defaillance).
Piege courant : L'amende recue par l'entreprise n'est PAS une defaillance du systeme — c'est une consequence. La defaillance c'est le comportement incorrect du logiciel.

Les 7 principes du test

#PrincipeExplication
1Le test montre la presence de defauts, pas leur absenceLe test peut montrer qu'il y a des defauts, mais ne peut pas prouver qu'il n'y en a pas.
2Le test exhaustif est impossibleTester toutes les combinaisons est impossible sauf pour les cas triviaux. Il faut prioriser (risques, techniques).
3Tester tot economise temps et argentLes defauts trouves tot coutent moins cher a corriger (shift-left).
4Les defauts se regroupentUn petit nombre de composants contient la majorite des defauts (principe de Pareto).
5L'usure des tests (Pesticide paradox)Repeter les memes tests finit par ne plus trouver de nouveaux defauts. Il faut varier les tests.
6Le test depend du contexteL'approche de test varie selon le contexte (e-commerce vs medical vs embarque).
7L'illusion de l'absence de defautsUn logiciel sans bug peut quand meme ne pas satisfaire les besoins des utilisateurs.
Comment choisir le bon principe dans une question d'examen
  1. La question parle de repeter les memes tests sans trouver de nouveaux defauts → Usure des tests (paradoxe du pesticide)
  2. La question parle d'un systeme sans bug mais qui ne satisfait pas les utilisateurs → Absence-of-defects fallacy
  3. La question parle de prioriser les tests car tout tester est impossible → Test exhaustif impossible
  4. La question parle de trouver plus de defauts dans certains modules → Regroupement des defauts (Pareto)
  5. La question mentionne tester tot, shift-left, cout de correction → Tester tot
  6. La question compare des approches differentes selon le domaine (medical vs jeu) → Contexte
Piege : "Tests wear out" et "Absence-of-defects" sont les 2 principes les plus confondus. Wear out = les TESTS s'usent (il faut varier). Absence = le PRODUIT sans bug peut etre inutile (il faut valider les besoins).

Testware

Produits d'activite crees pendant le processus de test : plan de test, cas de test, donnees de test, procedures de test, scripts automatises, resultats, rapports de defauts, chartes de test exploratoire.

Tracabilite

La tracabilite relie les elements de base de test aux cas de test et resultats. Elle permet : evaluer la couverture, l'analyse d'impact des changements (selectionner les tests de regression), la conformite aux audits, et des rapports comprehensibles.

Roles : Testeur vs Gestionnaire de test

TesteurGestionnaire de test
Reviser et contribuer aux plans de testPlanifier les tests, definir la strategie
Analyser, concevoir, implementer les testsCoordonner la strategie avec le PM et l'architecte
Preparer les donnees et l'environnementRediger les rapports de test
Executer et evaluer les resultatsRevoir les resultats, decider de la sortie
Utiliser les outils de testDecisions basees sur les resultats de test
Automatiser les tests (si applicable)Gerer les defauts et les risques

Competences essentielles du testeur

  • Connaissance du domaine metier
  • Competences techniques (outils, automatisation)
  • Pensee critique et analytique
  • Bon joueur d'equipe, communication
  • Attention aux details

Approche equipe entiere (Whole Team)

Tout membre de l'equipe peut effectuer des taches liees au test. Les testeurs collaborent avec les developpeurs ET les representants metier. Le testeur aide les representants metier a creer des tests d'acceptation adaptes. La qualite est la responsabilite de toute l'equipe.

Independance du test

AvantagesInconvenients
