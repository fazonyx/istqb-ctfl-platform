Impact du SDLC sur le test

Le choix du SDLC (sequentiel, iteratif, agile) impacte : la portee et le timing des activites de test, le niveau de detail de la documentation, les techniques choisies, l'etendue de l'automatisation, et le role du testeur.

Bonnes pratiques pour TOUS les SDLC

  • Pour chaque activite de developpement, il y a une activite de test correspondante
  • Chaque niveau de test a des objectifs specifiques
  • L'analyse et la conception des tests commencent pendant l'activite de developpement correspondante
  • Les testeurs participent des la definition et au raffinement des exigences

Modeles sequentiels vs iteratifs/incrementaux

Sequentiel (V-model, cascade)Iteratif/incremental (Agile, Scrum)
Phases lineaires, chaque phase termine avant la suivanteCycles courts (sprints/iterations)
Tests souvent a la fin du cycleTests a chaque iteration
Documentation formelleDocumentation legere
Exigences definies tot et stablesExigences evoluent continuellement
Feedback tardifFeedback rapide et frequent

Test-first : TDD, ATDD, BDD

ApprocheNiveauQui ecritDescription
TDDComposantDeveloppeurEcrire un test unitaire AVANT le code. Red-Green-Refactor. Code oriente.
ATDDSysteme/AcceptationEquipe (testeur, dev, metier)Tests derives des criteres d'acceptation AVANT le developpement.
BDDSysteme/AcceptationEquipeTests exprimes en langage naturel (Given/When/Then). Le comportement est central.

Approche Shift-left

Principe : tester le plus tot possible dans le SDLC. Exemples :

  • Reviser les exigences avant leur acceptation formelle
  • Ecrire des tests avant le code (TDD)
  • Executer des tests de performance au niveau composant
  • Effectuer des analyses statiques avant les tests dynamiques
Ce qui n'est PAS shift-left : ecrire un script de test avant de mettre en place la gestion de configuration (c'est juste mal organise, pas shift-left).

Retrospectives

Reunions a la fin d'un sprint/iteration pour discuter de ce qui a bien fonctionne, ce qui peut etre ameliore, et definir des actions d'amelioration continue.

Les retrospectives ne servent PAS a : trouver des defauts dans le produit, evaluer les performances individuelles, remplacer les tests.

Types de test

  • Fonctionnel : Que fait le systeme ? Verifie les fonctionnalites (completude, exactitude, pertinence)
  • Non-fonctionnel : Comment le systeme le fait ? Performance, utilisabilite, securite, fiabilite, portabilite
  • Boite noire : Basee sur les specifications (entrees/sorties), sans connaitre la structure interne
  • Boite blanche : Basee sur la structure interne du code (instructions, branches)
  • Confirmation (re-test) : Re-tester un defaut corrige pour verifier qu'il est resolu
  • Regression : Verifier qu'un changement n'a pas cause de nouveaux defauts dans le code existant
Confirmation = re-tester ce qui a echoue. Regression = re-tester ce qui marchait. Ce sont des activites DIFFERENTES !
Comment distinguer confirmation et regression dans un scenario
  1. Identifier les tests qui avaient echoue a l'execution precedente
  2. Ces tests, re-executes apres correction → ce sont des tests de confirmation
  3. Identifier les tests qui avaient reussi a l'execution precedente
  4. Ces tests, re-executes pour verifier qu'ils passent toujours → ce sont des tests de regression
Exemple : Execution 1 : TC1=FAIL, TC2=PASS. Apres correction, Execution 2 : TC1 est re-teste (confirmation), TC2 est re-teste (regression).
Piege : Si TC1 echoue ENCORE a l'Execution 2, puis est re-teste a l'Execution 3, c'est ENCORE de la confirmation (pas de la regression).

Test de maintenance : 3 declencheurs

  • Modification : Corrections, ameliorations, changements planifies (ex: mise a jour OS)
  • Changement d'environnement : Migration de plateforme, nouvelle base de donnees
  • Retrait (retirement) : Systeme mis hors service, migration des donnees a tester
Comment identifier un declencheur de maintenance
  1. Le systeme existant est modifie (correction, amelioration, hotfix) → Modification
  2. L'environnement change (nouvel OS, nouvelle DB, migration cloud) → Changement d'environnement
  3. Le systeme est retire/desactive (migration de donnees, archivage) → Retrait
Piege : Developper une NOUVELLE fonctionnalite (user story) n'est PAS de la maintenance — c'est du developpement normal suivi de tests de regression. La maintenance concerne un systeme DEJA en production.
