2.1. Le test dans le contexte d'un cycle de vie du developpement logiciel (SDLC)

Objectifs d'apprentissage :

FL-2.1.3 (K1) Rappeler les exemples d'approches de developpement pilotees par les tests

FL-2.1.6 (K2) Expliquer comment les retrospectives peuvent etre utilisees comme mecanisme d'amelioration des processus

Un modele de SDLC est une representation abstraite et de haut niveau du processus de developpement logiciel. Un modele de SDLC definit comment les differentes phases de developpement et les types d'activites effectuees dans ce processus sont lies les uns aux autres, tant logiquement que chronologiquement. Les exemples de modeles de SDLC comprennent : les modeles de developpement sequentiels (par exemple, modele en cascade, modele en V), les modeles de developpement iteratifs (par exemple, modele en spirale, prototypage) et les modeles de developpement incrementaux (par exemple, Unified Process).

Certaines activites au sein des processus de developpement logiciel peuvent egalement etre decrites par des methodes de developpement logiciel plus detaillees et des pratiques Agile. Les exemples comprennent : le developpement pilote par les tests d'acceptation (ATDD), le developpement pilote par le comportement (BDD), la conception pilotee par le domaine (DDD), l'Extreme Programming (XP), le developpement pilote par les fonctionnalites (FDD), Kanban, Lean IT, Scrum et le developpement pilote par les tests (TDD).

2.1.1. Impact du cycle de vie du developpement logiciel sur le test

Le test doit etre adapte au SDLC pour reussir. Le choix du SDLC a un impact sur :

  • La portee et le calendrier des activites de test (par exemple, niveaux de test et types de test)
  • Le niveau de detail de la documentation de test
  • Le choix des techniques de test et de l'approche de test
  • L'etendue de l'automatisation des tests
  • Le role et les responsabilites du testeur

Dans les modeles de developpement sequentiels, dans les phases initiales, les testeurs participent generalement aux revues d'exigences, a l'analyse de test et a la conception des tests. Le code executable est generalement cree dans les phases ulterieures, de sorte que le test dynamique ne peut generalement pas etre effectue tot dans le SDLC.

Dans certains modeles de developpement iteratifs et incrementaux, on suppose que chaque iteration livre un prototype fonctionnel ou un increment de produit. Cela implique que dans chaque iteration, le test statique et le test dynamique peuvent etre effectues a tous les niveaux de test. La livraison frequente d'increments necessite un retour rapide et des tests de regression etendus.

Le developpement logiciel Agile suppose que des changements peuvent survenir tout au long du projet. Par consequent, une documentation legere des produits d'activite et une automatisation extensive des tests pour faciliter le test de regression sont privilegiees dans les projets agiles. De plus, la plupart des tests manuels tendent a etre effectues en utilisant des techniques de test basees sur l'experience (voir section 4.4) qui ne necessitent pas d'analyse et de conception de test prealables approfondies.

2.1.2. Cycle de vie du developpement logiciel et bonnes pratiques de test

Les bonnes pratiques de test, independamment du modele de SDLC choisi, comprennent les suivantes :

  • Pour chaque activite de developpement logiciel, il existe une activite de test correspondante, de sorte que toutes les activites de developpement sont soumises au controle qualite
  • Les differents niveaux de test (voir chapitre 2.2.1) ont des objectifs de test specifiques et differents, ce qui permet au test d'etre suffisamment complet tout en evitant la redondance
  • L'analyse et la conception de test pour un niveau de test donne commencent pendant la phase de developpement correspondante du SDLC, afin que le test puisse respecter le principe du test precoce (voir section 1.3)
  • Les testeurs participent a la revue des produits d'activite des que les ebauches de ces produits sont disponibles, afin que ce test plus precoce et cette detection des defauts puissent soutenir le shift-left (voir section 2.1.5).

2.1.3. Le test comme moteur du developpement logiciel

TDD, ATDD et BDD sont des approches de developpement similaires, ou les tests sont definis comme un moyen de diriger le developpement. Chacune de ces approches met en oeuvre le principe du test precoce (voir section 1.3) et suit le shift-left (voir section 2.1.5), puisque les tests sont definis avant que le code ne soit ecrit. Elles soutiennent un modele de developpement iteratif. Ces approches sont caracterisees comme suit :

Developpement pilote par les tests (TDD) :

  • Dirige le codage par les cas de test (au lieu d'une conception logicielle extensive) (Beck 2003)
  • Les tests sont ecrits en premier, puis le code est ecrit pour satisfaire les tests, et ensuite les tests et le code sont refactorises

Developpement pilote par les tests d'acceptation (ATDD) (voir section 4.5.3) :

  • Derive les tests des criteres d'acceptation dans le cadre du processus de conception du systeme (Gartner 2011)
  • Les tests sont ecrits avant que la partie de l'application ne soit developpee pour satisfaire les tests

Developpement pilote par le comportement (BDD) :

  • Exprime le comportement souhaite d'une application avec des cas de test ecrits dans une forme simple de langage naturel, facile a comprendre par les parties prenantes - generalement en utilisant le format Given/When/Then (Chelimsky 2010)
  • Les cas de test doivent ensuite etre automatiquement traduits en tests executables

Pour toutes les approches ci-dessus, les tests peuvent persister sous forme de tests automatises pour assurer la qualite du code lors de futures adaptations / refactorisations.

Attention examen

TDD = test unitaire ecrit par le developpeur (red-green-refactor). ATDD = test d'acceptation defini par l'equipe a partir des criteres d'acceptation. BDD = langage naturel Given/When/Then compris par les parties prenantes. Ne les confondez pas.

2.1.4. DevOps et test

DevOps est une approche organisationnelle visant a creer une synergie en faisant travailler ensemble le developpement (y compris le test) et les operations pour atteindre un ensemble d'objectifs communs. DevOps necessite un changement culturel au sein d'une organisation pour combler les ecarts entre le developpement (y compris le test) et les operations tout en traitant leurs fonctions avec une valeur egale. DevOps favorise l'autonomie des equipes, le retour rapide, les chaines d'outils integrees et les pratiques techniques comme l'integration continue (CI) et la livraison continue (CD). Cela permet aux equipes de construire, tester et livrer du code de haute qualite plus rapidement grace a un pipeline de livraison DevOps (Kim 2016).

Du point de vue du test, certains des avantages de DevOps sont les suivants :

  • Retour rapide sur la qualite du code et sur le fait que les changements affectent negativement ou non le code existant
  • La CI favorise le shift-left dans le test (voir section 2.1.5) en encourageant les developpeurs a soumettre du code de haute qualite accompagne de tests de composants et d'analyse statique
  • Les processus automatises sont favorises comme CI/CD qui facilite l'etablissement d'environnements de test stables
  • La visibilite sur les caracteristiques de qualite non fonctionnelles augmente (par exemple, efficacite de performance, fiabilite)
  • L'automatisation via un pipeline de livraison reduit le besoin de tests manuels repetitifs
  • Le risque de regression est minimise grace a l'echelle et a la portee des tests de regression automatises

DevOps n'est pas sans risques ni defis, qui comprennent :

  • Le pipeline de livraison DevOps doit etre defini et etabli
  • Les outils CI/CD doivent etre introduits et maintenus
  • L'automatisation des tests necessite des ressources supplementaires et peut etre difficile a etablir et a maintenir

Bien que DevOps implique un haut niveau de tests automatises, le test manuel - en particulier du point de vue de l'utilisateur - reste necessaire.

2.1.5. Shift-left

Le principe du test precoce (voir section 1.3) est parfois appele shift-left car c'est une approche ou le test est effectue plus tot dans le SDLC. Le shift-left suggere essentiellement que le test devrait etre fait plus tot (par exemple, sans attendre que le code soit implemente ou que les composants soient integres), mais cela ne signifie pas que le test plus tard dans le SDLC devrait etre neglige.

Il existe quelques bonnes pratiques qui illustrent comment realiser un "shift-left" dans le test, notamment :

  • Revoir la specification du point de vue des testeurs. Ces activites de revue des specifications trouvent souvent des defauts potentiels, tels que des ambiguites, des incompletudes et des incoherences
  • Ecrire les cas de test avant que le code ne soit ecrit et executer le code dans un harnais de test pendant l'implementation du code
  • Utiliser la CI et encore mieux la CD car elle apporte un retour rapide et des tests de composants automatises pour accompagner le code source lorsqu'il est soumis au depot de code
  • Effectuer l'analyse statique du code source avant le test dynamique, ou dans le cadre d'un processus automatise
  • Effectuer les tests non fonctionnels des le niveau du test de composant, lorsque c'est possible. C'est une forme de shift-left car ces types de tests non fonctionnels tendent a etre effectues plus tard dans le SDLC lorsqu'un systeme complet et un environnement de test representatif sont disponibles

Le shift-left peut entrainer des formations, des efforts et/ou des couts supplementaires plus tot dans le processus, mais devrait permettre d'economiser des efforts et/ou des couts plus tard dans le processus.

Pour le shift-left, il est important que les parties prenantes soient convaincues et adherent a ce concept.

Attention examen

Ecrire un script de test AVANT de mettre en place la gestion de configuration n'est PAS du shift-left — c'est juste mal organise. Le shift-left signifie effectuer les activites de test plus tot dans le SDLC (revues, TDD, analyse statique), pas faire les choses dans le desordre.

2.1.6. Retrospectives et amelioration des processus

Les retrospectives ont souvent lieu a la fin d'un projet ou d'une iteration, a un jalon de mise en production, ou peuvent etre tenues en cas de besoin. Le calendrier et l'organisation des retrospectives dependent du modele de SDLC particulier suivi. Lors de ces reunions, les participants (pas seulement les testeurs, mais aussi par exemple les developpeurs, les architectes, le product owner, les analystes metier) discutent :

  • Qu'est-ce qui a fonctionne et devrait etre conserve ?
  • Qu'est-ce qui n'a pas fonctionne et pourrait etre ameliore ?
  • Comment integrer les ameliorations et conserver les succes a l'avenir ?

Les resultats doivent etre enregistres et font normalement partie du rapport de cloture des tests (voir section 5.3.2). Les retrospectives sont essentielles pour la mise en oeuvre reussie de l'amelioration continue, et il est important que toute amelioration recommandee fasse l'objet d'un suivi.

Les avantages typiques pour le test comprennent :

  • Augmentation de l'efficacite / efficience du test (par exemple, en mettant en oeuvre des suggestions d'amelioration des processus)
  • Augmentation de la qualite du testware (par exemple, en revoyant conjointement les processus de test)
  • Cohesion d'equipe et apprentissage (par exemple, grace a l'opportunite de soulever des problemes et de proposer des points d'amelioration)
  • Amelioration de la qualite de la base de test (par exemple, les insuffisances dans l'etendue et la qualite des exigences pourraient etre traitees et resolues)
  • Meilleure cooperation entre le developpement et le test (par exemple, car la collaboration est revue et optimisee regulierement)
A retenir
  • Le SDLC choisi impacte la portee, le timing, la documentation, l'automatisation et les roles de test
  • Bonne pratique universelle : chaque activite de dev a une activite de test correspondante
  • TDD (dev, unitaire), ATDD (equipe, acceptation), BDD (Given/When/Then, langage naturel)
  • DevOps = dev + ops ensemble, favorise CI/CD et automatisation des tests
  • Shift-left = tester plus tot (revues, TDD, analyse statique), pas negliger les tests tardifs
  • Retrospectives : qu'est-ce qui a marche ? Qu'est-ce a ameliorer ? Comment conserver les succes ?

2.2. Niveaux de test et types de test

Objectifs d'apprentissage :
FL-2.2.1 (K2) Distinguer les differents niveaux de test
FL-2.2.2 (K2) Distinguer les differents types de test
FL-2.2.3 (K2) Distinguer le test de confirmation du test de regression

Les niveaux de test sont des groupes d'activites de test qui sont organises et geres ensemble. Chaque niveau de test est une instance du processus de test, effectuee en relation avec le logiciel a une phase donnee du developpement, des composants individuels aux systemes complets ou, le cas echeant, aux systemes de systemes.

Les niveaux de test sont lies aux autres activites du SDLC. Dans les modeles de SDLC sequentiels, les niveaux de test sont souvent definis de telle sorte que les criteres de sortie d'un niveau font partie des criteres d'entree du niveau suivant. Dans certains modeles iteratifs, cela peut ne pas s'appliquer. Les activites de developpement peuvent s'etendre sur plusieurs niveaux de test. Les niveaux de test peuvent se chevaucher dans le temps.

Les types de test sont des groupes d'activites de test lies a des caracteristiques de qualite specifiques et la plupart de ces activites de test peuvent etre effectuees a chaque niveau de test.

2.2.1. Niveaux de test

Dans ce syllabus, les cinq niveaux de test suivants sont decrits :

  • Le test de composant (egalement appele test unitaire) se concentre sur le test des composants de maniere isolee. Il necessite souvent un support specifique, tel que des harnais de test ou des frameworks de test unitaire. Le test de composant est normalement effectue par les developpeurs dans leurs environnements de developpement.
  • Le test d'integration de composants (egalement appele test d'integration unitaire) se concentre sur le test des interfaces et des interactions entre les composants. Le test d'integration de composants depend fortement de la strategie d'integration comme ascendante (bottom-up), descendante (top-down) ou big-bang.
  • Le test systeme se concentre sur le comportement global et les capacites d'un systeme ou produit entier, incluant souvent le test fonctionnel des taches de bout en bout et le test non fonctionnel des caracteristiques de qualite. Pour certaines caracteristiques de qualite non fonctionnelles, il est preferable de les tester sur un systeme complet dans un environnement de test representatif (par exemple, l'utilisabilite). L'utilisation de simulations de sous-systemes est egalement possible. Le test systeme peut etre effectue par une equipe de test independante et est lie aux specifications du systeme.
  • Le test d'integration systeme se concentre sur le test des interfaces du systeme sous test avec d'autres systemes et services externes. Le test d'integration systeme necessite des environnements de test adaptes, de preference similaires a l'environnement operationnel.
  • Le test d'acceptation se concentre sur la validation et la demonstration de la disponibilite au deploiement, ce qui signifie que le systeme repond aux besoins metier de l'utilisateur. Idealement, le test d'acceptation devrait etre effectue par les utilisateurs vises. Les principales formes de test d'acceptation sont : le test d'acceptation utilisateur (UAT), le test d'acceptation operationnelle, le test d'acceptation contractuelle et le test d'acceptation reglementaire, le test alpha et le test beta.

Les niveaux de test se distinguent par la liste non exhaustive d'attributs suivante, pour eviter le chevauchement des activites de test :

  • Objet de test
  • Objectifs de test
  • Base de test
  • Defauts et defaillances
  • Approche et responsabilites

2.2.2. Types de test

De nombreux types de test existent et peuvent etre appliques dans les projets. Dans ce syllabus, les quatre types de test suivants sont abordes :

Le test fonctionnel evalue les fonctions qu'un composant ou un systeme devrait effectuer. Les fonctions sont "ce que" l'objet de test devrait faire. L'objectif principal du test fonctionnel est de verifier la completude fonctionnelle, la correction fonctionnelle et la pertinence fonctionnelle.

Le test non fonctionnel evalue les attributs autres que les caracteristiques fonctionnelles d'un composant ou d'un systeme. Le test non fonctionnel est le test de "comment le systeme se comporte". L'objectif principal du test non fonctionnel est de verifier les caracteristiques de qualite non fonctionnelles. La norme ISO/IEC 25010 fournit la classification suivante des caracteristiques de qualite non fonctionnelles :

  • Efficacite de performance
  • Compatibilite
  • Utilisabilite (egalement connue sous le nom de capacite d'interaction)
  • Fiabilite
  • Securite
  • Maintenabilite
  • Portabilite (egalement connue sous le nom de flexibilite)
  • Surete

Il est parfois approprie que le test non fonctionnel commence tot dans le SDLC (par exemple, dans le cadre des revues ou du test de composant). De nombreux tests non fonctionnels sont derives des tests fonctionnels car ils utilisent les memes tests fonctionnels, mais verifient que lors de l'execution de la fonction, une contrainte non fonctionnelle est satisfaite (par exemple, verifier qu'une fonction s'execute dans un temps specifie, ou qu'une fonction peut etre portee sur une nouvelle plateforme). La decouverte tardive de defauts non fonctionnels peut constituer une menace serieuse pour le succes d'un projet. Le test non fonctionnel necessite parfois un environnement de test tres specifique, comme un laboratoire d'utilisabilite pour le test d'utilisabilite.

Le test boite noire (voir section 4.2) est base sur les specifications et derive les tests de la documentation non liee a la structure interne de l'objet de test. L'objectif principal du test boite noire est de verifier le comportement du systeme par rapport a ses specifications.

Le test boite blanche (voir section 4.3) est base sur la structure et derive les tests de l'implementation ou de la structure interne du systeme (par exemple, le code, l'architecture, les flux de travail et les flux de donnees). L'objectif principal du test boite blanche est de couvrir la structure sous-jacente par les tests a un niveau acceptable.

Les quatre types de test mentionnes ci-dessus peuvent etre appliques a tous les niveaux de test, bien que l'accent soit different a chaque niveau. Differentes techniques de test peuvent etre utilisees pour deriver les conditions de test et les cas de test pour tous les types de test mentionnes.

2.2.3. Test de confirmation et test de regression

Des modifications sont generalement apportees a un composant ou un systeme soit pour l'ameliorer en ajoutant une nouvelle fonctionnalite, soit pour le corriger en supprimant un defaut. Le test devrait alors egalement inclure le test de confirmation et le test de regression.

Le test de confirmation confirme qu'un defaut original a ete corrige avec succes. Selon le risque, on peut tester la version corrigee du logiciel de plusieurs facons, notamment :

  • en executant tous les tests qui avaient precedemment echoue a cause du defaut, ou aussi en
  • ajoutant de nouveaux tests pour couvrir les modifications necessaires a la correction du defaut

Cependant, lorsque le temps ou l'argent est limite pour corriger les defauts, le test de confirmation peut se limiter a simplement executer les etapes de test qui devraient reproduire la defaillance causee par le defaut et verifier que la defaillance ne se produit pas.

Le test de regression confirme qu'aucune consequence indesirable n'a ete causee par une modification, y compris une correction qui a deja fait l'objet d'un test de confirmation. Ces consequences indesirables pourraient affecter le meme composant ou la modification a ete effectuee, d'autres composants dans le meme systeme, ou meme d'autres systemes connectes. Le test de regression peut ne pas se limiter a l'objet de test lui-meme mais peut egalement concerner l'environnement. Il est conseille d'effectuer d'abord une analyse d'impact pour reconnaitre l'etendue du test de regression. L'analyse d'impact montre quelles parties du logiciel pourraient etre affectees.

Les suites de test de regression sont executees de nombreuses fois et generalement le nombre de cas de test de regression augmente a chaque iteration ou version, de sorte que le test de regression est un candidat de choix pour l'automatisation. L'automatisation des tests devrait commencer tot dans le projet. Lorsque la CI est utilisee, comme dans DevOps (voir section 2.1.4), il est recommande d'inclure egalement des tests de regression automatises. Selon la situation, cela peut inclure des tests de regression a differents niveaux de test.

Le test de confirmation et/ou le test de regression pour l'objet de test sont necessaires a tous les niveaux de test si des defauts sont corriges et/ou des modifications sont effectuees a ces niveaux de test.

Attention examen

Si TC1 echoue en execution 1 et est re-teste en execution 2, c'est de la confirmation. Si TC2 a reussi en execution 1 et est re-teste en execution 2 apres un changement, c'est de la regression. Le test de regression est un candidat ideal pour l'automatisation.

A retenir
  • 5 niveaux : composant, integration composant, systeme, integration systeme, acceptation
  • 4 types : fonctionnel (quoi), non fonctionnel (comment), boite noire (specs), boite blanche (structure)
  • Confirmation = re-tester ce qui a echoue apres correction. Regression = re-tester ce qui marchait apres changement
  • Le test de regression croit a chaque iteration et doit etre automatise

2.3. Test de maintenance

Objectifs d'apprentissage :
FL-2.3.1 (K2) Resumer le test de maintenance et ses declencheurs

Il existe differentes categories de maintenance : elle peut etre corrective, adaptive aux changements de l'environnement ou viser a ameliorer les performances ou la maintenabilite (voir ISO/IEC 14764 pour les details). La maintenance peut donc impliquer des versions/deploiements planifies et des versions/deploiements non planifies (correctifs urgents). Une analyse d'impact peut etre effectuee avant qu'une modification ne soit apportee, pour aider a decider si la modification doit etre faite, sur la base des consequences potentielles dans d'autres parties du systeme. Tester les modifications apportees a un systeme operationnel comprend a la fois l'evaluation du succes de l'implementation de la modification et la verification de regressions possibles dans les parties du systeme qui restent inchangees (ce qui represente generalement la majeure partie du systeme).

La portee du test de maintenance depend generalement de :

  • Le degre de risque de la modification
  • La taille du systeme existant
  • La taille de la modification

Les declencheurs de la maintenance et du test de maintenance peuvent etre classes comme suit :

  • Les modifications, telles que les ameliorations planifiees (c'est-a-dire basees sur les versions), les corrections ou les correctifs urgents.
  • Les mises a niveau ou migrations de l'environnement operationnel, par exemple d'une plateforme a une autre, ce qui peut necessiter des tests associes au nouvel environnement ainsi qu'au logiciel modifie, ou des tests de conversion de donnees lorsque des donnees d'une autre application sont migrees dans le systeme maintenu.
  • Le retrait, par exemple lorsqu'une application arrive en fin de vie. Lorsqu'un systeme est retire, cela peut necessiter des tests d'archivage des donnees si de longues periodes de conservation des donnees sont requises. Des tests de restauration et de recuperation des procedures apres archivage peuvent egalement etre necessaires dans le cas ou certaines donnees seraient requises pendant la periode d'archivage.
A retenir
  • 3 declencheurs de test de maintenance : modifications (ameliorations, corrections), mises a jour/migrations, retrait
  • L'analyse d'impact determine la portee du test de maintenance
  • Le test de maintenance inclut test de confirmation ET test de regression

Impact du SDLC sur le test

Le choix du SDLC (sequentiel, iteratif, agile) impacte : la portee et le timing des activites de test, le niveau de detail de la documentation, les techniques choisies, l'etendue de l'automatisation, et le role du testeur.

Bonnes pratiques pour TOUS les SDLC

  • Pour chaque activite de developpement, il y a une activite de test correspondante
  • Chaque niveau de test a des objectifs specifiques
  • L'analyse et la conception des tests commencent pendant l'activite de developpement correspondante
  • Les testeurs participent des la definition et au raffinement des exigences

Approche Shift-left

Principe : tester le plus tot possible dans le SDLC. Exemples :

  • Reviser les exigences avant leur acceptation formelle
  • Ecrire des tests avant le code (TDD)
  • Executer des tests de performance au niveau composant
  • Effectuer des analyses statiques avant les tests dynamiques
Ce qui n'est PAS shift-left : ecrire un script de test avant de mettre en place la gestion de configuration (c'est juste mal organise, pas shift-left).

Retrospectives

Reunions a la fin d'un sprint/iteration pour discuter de ce qui a bien fonctionne, ce qui peut etre ameliore, et definir des actions d'amelioration continue.

Les retrospectives ne servent PAS a : trouver des defauts dans le produit, evaluer les performances individuelles, remplacer les tests.

  • Boite noire : Basee sur les specifications (entrees/sorties), sans connaitre la structure interne
  • Boite blanche : Basee sur la structure interne du code (instructions, branches)
  • Confirmation (re-test) : Re-tester un defaut corrige pour verifier qu'il est resolu
  • Regression : Verifier qu'un changement n'a pas cause de nouveaux defauts dans le code existant
Confirmation = re-tester ce qui a echoue. Regression = re-tester ce qui marchait. Ce sont des activites DIFFERENTES !
Comment distinguer confirmation et regression dans un scenario
  1. Identifier les tests qui avaient echoue a l'execution precedente
  2. Ces tests, re-executes apres correction → ce sont des tests de confirmation
  3. Identifier les tests qui avaient reussi a l'execution precedente
  4. Ces tests, re-executes pour verifier qu'ils passent toujours → ce sont des tests de regression
Exemple : Execution 1 : TC1=FAIL, TC2=PASS. Apres correction, Execution 2 : TC1 est re-teste (confirmation), TC2 est re-teste (regression).
Piege : Si TC1 echoue ENCORE a l'Execution 2, puis est re-teste a l'Execution 3, c'est ENCORE de la confirmation (pas de la regression).

Test de maintenance : 3 declencheurs

  • Modification : Corrections, ameliorations, changements planifies (ex: mise a jour OS)
  • Changement d'environnement : Migration de plateforme, nouvelle base de donnees
  • Retrait (retirement) : Systeme mis hors service, migration des donnees a tester
Comment identifier un declencheur de maintenance
  1. Le systeme existant est modifie (correction, amelioration, hotfix) → Modification
  2. L'environnement change (nouvel OS, nouvelle DB, migration cloud) → Changement d'environnement
  3. Le systeme est retire/desactive (migration de donnees, archivage) → Retrait
Piege : Developper une NOUVELLE fonctionnalite (user story) n'est PAS de la maintenance — c'est du developpement normal suivi de tests de regression. La maintenance concerne un systeme DEJA en production.
