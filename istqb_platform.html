Chapitre 1 - Fondamentaux du test ▶

Pourquoi le test est necessaire

Le test est necessaire pour detecter les defauts, reduire les risques de defaillances en production, satisfaire les exigences contractuelles et reglementaires, et contribuer au succes du projet.

Les 7 objectifs du test

  • Evaluer les produits d'activite (exigences, user stories, conception, code)
  • Detecter les defaillances et les defauts
  • Assurer la couverture requise d'un objet de test
  • Reduire le niveau de risque d'un logiciel de qualite insuffisante
  • Verifier si les exigences specifiees sont satisfaites
  • Verifier la conformite aux exigences contractuelles, legales et reglementaires
  • Fournir des informations aux parties prenantes pour prise de decision eclairee
Attention : "Corriger les defauts" n'est PAS un objectif du test. Corriger = debogage (activite du developpeur).

Test vs QA vs Debogage

  • Test : Activite orientee produit, vise a detecter les defauts et evaluer la qualite
  • QA (Assurance Qualite) : Activite orientee processus, vise a ameliorer les processus pour prevenir les defauts
  • Debogage : Activite du developpeur, consiste a trouver, analyser et supprimer la cause d'une defaillance

Chaine causale : Erreur - Defaut - Defaillance

  • Cause racine : Raison fondamentale (fatigue, pression, manque de formation...)
  • Erreur : Action humaine produisant un resultat incorrect
  • Defaut (bug) : Imperfection dans un produit d'activite (code, document...)
  • Defaillance : Evenement ou le systeme ne fait pas ce qu'il devrait
Un defaut n'entraine pas toujours une defaillance. Une defaillance peut aussi venir de l'environnement (radiation, pollution).
Comment identifier erreur/defaut/defaillance dans un scenario d'examen
  1. Reperer l'action humaine incorrecte → c'est l'erreur
  2. Reperer le produit d'activite impacte (code, doc, spec) → le defaut est LA-DEDANS
  3. Reperer le comportement observable incorrect du systeme en execution → c'est la defaillance
  4. Chercher le pourquoi profond de l'erreur humaine (fatigue, pression...) → c'est la cause racine
Exemple : Un dev fatigue (cause racine) ecrit ">" au lieu de ">=" (erreur). Le code contient la mauvaise condition (defaut). Le systeme refuse 18 ans alors qu'il devrait accepter (defaillance).
Piege courant : L'amende recue par l'entreprise n'est PAS une defaillance du systeme — c'est une consequence. La defaillance c'est le comportement incorrect du logiciel.

Les 7 principes du test

#PrincipeExplication
1Le test montre la presence de defauts, pas leur absenceLe test peut montrer qu'il y a des defauts, mais ne peut pas prouver qu'il n'y en a pas.
2Le test exhaustif est impossibleTester toutes les combinaisons est impossible sauf pour les cas triviaux. Il faut prioriser (risques, techniques).
3Tester tot economise temps et argentLes defauts trouves tot coutent moins cher a corriger (shift-left).
4Les defauts se regroupentUn petit nombre de composants contient la majorite des defauts (principe de Pareto).
5L'usure des tests (Pesticide paradox)Repeter les memes tests finit par ne plus trouver de nouveaux defauts. Il faut varier les tests.
6Le test depend du contexteL'approche de test varie selon le contexte (e-commerce vs medical vs embarque).
7L'illusion de l'absence de defautsUn logiciel sans bug peut quand meme ne pas satisfaire les besoins des utilisateurs.
Comment choisir le bon principe dans une question d'examen
  1. La question parle de repeter les memes tests sans trouver de nouveaux defauts → Usure des tests (paradoxe du pesticide)
  2. La question parle d'un systeme sans bug mais qui ne satisfait pas les utilisateurs → Absence-of-defects fallacy
  3. La question parle de prioriser les tests car tout tester est impossible → Test exhaustif impossible
  4. La question parle de trouver plus de defauts dans certains modules → Regroupement des defauts (Pareto)
  5. La question mentionne tester tot, shift-left, cout de correction → Tester tot
  6. La question compare des approches differentes selon le domaine (medical vs jeu) → Contexte
Piege : "Tests wear out" et "Absence-of-defects" sont les 2 principes les plus confondus. Wear out = les TESTS s'usent (il faut varier). Absence = le PRODUIT sans bug peut etre inutile (il faut valider les besoins).

Testware

Produits d'activite crees pendant le processus de test : plan de test, cas de test, donnees de test, procedures de test, scripts automatises, resultats, rapports de defauts, chartes de test exploratoire.

Tracabilite

La tracabilite relie les elements de base de test aux cas de test et resultats. Elle permet : evaluer la couverture, l'analyse d'impact des changements (selectionner les tests de regression), la conformite aux audits, et des rapports comprehensibles.

Competences essentielles du testeur

  • Connaissance du domaine metier
  • Competences techniques (outils, automatisation)
  • Pensee critique et analytique
  • Bon joueur d'equipe, communication
  • Attention aux details

Approche equipe entiere (Whole Team)

Tout membre de l'equipe peut effectuer des taches liees au test. Les testeurs collaborent avec les developpeurs ET les representants metier. Le testeur aide les representants metier a creer des tests d'acceptation adaptes. La qualite est la responsabilite de toute l'equipe.

Chapitre 2 - Test dans le cycle de vie du developpement logiciel ▶

Impact du SDLC sur le test

Le choix du SDLC (sequentiel, iteratif, agile) impacte : la portee et le timing des activites de test, le niveau de detail de la documentation, les techniques choisies, l'etendue de l'automatisation, et le role du testeur.

Bonnes pratiques pour TOUS les SDLC

  • Pour chaque activite de developpement, il y a une activite de test correspondante
  • Chaque niveau de test a des objectifs specifiques
  • L'analyse et la conception des tests commencent pendant l'activite de developpement correspondante
  • Les testeurs participent des la definition et au raffinement des exigences

Modeles sequentiels vs iteratifs/incrementaux

Sequentiel (V-model, cascade)Iteratif/incremental (Agile, Scrum)
Phases lineaires, chaque phase termine avant la suivanteCycles courts (sprints/iterations)
Tests souvent a la fin du cycleTests a chaque iteration
Documentation formelleDocumentation legere
Exigences definies tot et stablesExigences evoluent continuellement
Feedback tardifFeedback rapide et frequent

Test-first : TDD, ATDD, BDD

ApprocheNiveauQui ecritDescription
TDDComposantDeveloppeurEcrire un test unitaire AVANT le code. Red-Green-Refactor. Code oriente.
ATDDSysteme/AcceptationEquipe (testeur, dev, metier)Tests derives des criteres d'acceptation AVANT le developpement.
BDDSysteme/AcceptationEquipeTests exprimes en langage naturel (Given/When/Then). Le comportement est central.

Approche Shift-left

Principe : tester le plus tot possible dans le SDLC. Exemples :

  • Reviser les exigences avant leur acceptation formelle
  • Ecrire des tests avant le code (TDD)
  • Executer des tests de performance au niveau composant
  • Effectuer des analyses statiques avant les tests dynamiques
Ce qui n'est PAS shift-left : ecrire un script de test avant de mettre en place la gestion de configuration (c'est juste mal organise, pas shift-left).

Retrospectives

Reunions a la fin d'un sprint/iteration pour discuter de ce qui a bien fonctionne, ce qui peut etre ameliore, et definir des actions d'amelioration continue.

Les retrospectives ne servent PAS a : trouver des defauts dans le produit, evaluer les performances individuelles, remplacer les tests.

Types de test

  • Fonctionnel : Que fait le systeme ? Verifie les fonctionnalites (completude, exactitude, pertinence)
  • Non-fonctionnel : Comment le systeme le fait ? Performance, utilisabilite, securite, fiabilite, portabilite
  • Boite noire : Basee sur les specifications (entrees/sorties), sans connaitre la structure interne
  • Boite blanche : Basee sur la structure interne du code (instructions, branches)
  • Confirmation (re-test) : Re-tester un defaut corrige pour verifier qu'il est resolu
  • Regression : Verifier qu'un changement n'a pas cause de nouveaux defauts dans le code existant
Confirmation = re-tester ce qui a echoue. Regression = re-tester ce qui marchait. Ce sont des activites DIFFERENTES !
Comment distinguer confirmation et regression dans un scenario
  1. Identifier les tests qui avaient echoue a l'execution precedente
  2. Ces tests, re-executes apres correction → ce sont des tests de confirmation
  3. Identifier les tests qui avaient reussi a l'execution precedente
  4. Ces tests, re-executes pour verifier qu'ils passent toujours → ce sont des tests de regression
Exemple : Execution 1 : TC1=FAIL, TC2=PASS. Apres correction, Execution 2 : TC1 est re-teste (confirmation), TC2 est re-teste (regression).
Piege : Si TC1 echoue ENCORE a l'Execution 2, puis est re-teste a l'Execution 3, c'est ENCORE de la confirmation (pas de la regression).

Test de maintenance : 3 declencheurs

  • Modification : Corrections, ameliorations, changements planifies (ex: mise a jour OS)
  • Changement d'environnement : Migration de plateforme, nouvelle base de donnees
  • Retrait (retirement) : Systeme mis hors service, migration des donnees a tester
Comment identifier un declencheur de maintenance
  1. Le systeme existant est modifie (correction, amelioration, hotfix) → Modification
  2. L'environnement change (nouvel OS, nouvelle DB, migration cloud) → Changement d'environnement
  3. Le systeme est retire/desactive (migration de donnees, archivage) → Retrait
Piege : Developper une NOUVELLE fonctionnalite (user story) n'est PAS de la maintenance — c'est du developpement normal suivi de tests de regression. La maintenance concerne un systeme DEJA en production.

Chapitre 3 - Test statique ▶

Produits examinables par test statique

  • Specifications d'exigences, user stories, epics
  • Code source
  • Plans de test, cas de test, procedures de test
  • Documents de conception (architecture, diagrammes)
  • Contrats, plans de projet, calendriers
Ce qui NE PEUT PAS etre revise par test statique : code compile/encrypte (non lisible par un humain), code executable tiers.

Valeur du test statique

Trouve par statique seulTrouve par dynamique seulTrouve par les deux
Ecarts par rapport aux standards de codageDefaillances a l'executionLacunes de couverture
Defauts dans les exigences (ambiguites, contradictions)Problemes de performance reelsDefauts de codage
Defauts de conception (ex: fonctions non utilisees)Comportements inattendusProblemes d'interface
Ecarts dans la tracabilite, manque de couverture securite

Feedback precoce : benefices

  • Aide a eviter les malentendus sur les exigences
  • Reduit le cout de correction (defauts trouves tres tot)
  • Ameliore la communication dans l'equipe
  • Permet de detecter les incoherences avant l'implementation

Processus de revue : 5 etapes dans l'ordre

1. Planification → 2. Initiation de la revue → 3. Revue individuelle → 4. Communication et analyse → 5. Correction et rapport
EtapeDescription
1. PlanificationDefinir la portee, les criteres, l'effort, les roles, les criteres d'entree/sortie
2. Initiation de la revueDistribuer le produit d'activite et les supports aux reviseurs, expliquer la portee et les objectifs
3. Revue individuelleChaque reviseur examine le produit et note les defauts potentiels, questions et suggestions
4. Communication et analyseDiscuter des defauts trouves, analyser, evaluer et decider du statut de chaque anomalie
5. Correction et rapportCreer les rapports de defauts, corriger les defauts trouves, rapporter les metriques
Comment retenir l'ordre du processus de revue
  1. Planification — on decide QUOI revoir, QUI participe, QUAND
  2. Initiation — on DISTRIBUE le document aux reviseurs
  3. Revue individuelle — chacun EXAMINE seul le document
  4. Communication — on se REUNIT pour discuter des anomalies
  5. Correction — on CORRIGE les defauts et on RAPPORTE
Moyen mnemotechnique : P-I-R-C-C = "PIRaté ça Corrige !" — Planifier, Initier, Revoir, Communiquer, Corriger.
Piege : La question decrit les 5 activites dans le desordre et te demande la bonne sequence. Identifie chaque description : "distribuer les documents" = Initiation (pas Planification !).

Facteurs de succes des revues

  • Objectifs clairs definis a l'avance
  • Choisir le bon type de revue selon les objectifs
  • Les reviseurs ont suffisamment de temps pour preparer
  • Le management soutient le processus de revue
  • Les revues font partie de la culture d'entreprise
  • Formation adequate des participants
  • Diviser les grands documents en petites parties
  • Les defauts trouves sont reconnus et traites objectivement (pas de blame)
  • Pas de comportements indiquant l'ennui, l'exasperation ou l'hostilite
Attention : lors des revues, on trouve des DEFAUTS, pas des defaillances ! Les defaillances apparaissent uniquement lors de l'execution (test dynamique).

Chapitre 4 - Techniques de test (LE PLUS IMPORTANT) ▶

Boite noire vs Boite blanche vs Basee sur l'experience

CategorieBaseQuand l'utiliser
Boite noireSpecifications, exigences, comportementQuand les specifications sont disponibles, tout niveau de test
Boite blancheStructure interne du codeTest de composant, mesure de couverture de code
Basee sur l'experienceConnaissance et expertise du testeurQuand les specs sont limitees, en complement des autres techniques

Partitions d'equivalence (EP)

  • Diviser les entrees en groupes (partitions) ou le systeme se comporte de la meme maniere
  • Partition valide : valeurs acceptees par le systeme
  • Partition invalide : valeurs rejetees par le systeme
  • Chaque valeur appartient a exactement UNE partition
  • Un seul cas de test par partition suffit (representant)
Couverture EP = partitions testees / total partitions x 100%

Exemple : champ age 18-65. Partitions : <18 (invalide), 18-65 (valide), >65 (invalide). 3 partitions au total.

Comment resoudre un exercice EP en 4 etapes
  1. Identifier la variable d'entree et ses contraintes (ex: "age entre 18 et 65")
  2. Lister les partitions : une valide (18-65), les invalides (<18, >65). S'il y a des sous-regles, creer des partitions supplementaires
  3. Choisir un representant par partition (n'importe quelle valeur dans la plage : 25 pour 18-65, 10 pour <18, 70 pour >65)
  4. Compter : couverture = partitions testees / total partitions x 100%
Exemple : D = CY - BY. Partitions : D<0 (erreur), 0<=D<18 (etudiant), 18<=D<65 (normal), D>=65 (retraite) = 4 partitions. Si 2 sont deja couvertes, il faut 2 tests supplementaires.
Piege : Lis bien les bornes ! "depasse 100$" signifie >100, pas >=100. "entre 0 et 2 inclus" signifie 0, 1 et 2 sont dans la partition.

BVA 2 valeurs (par defaut dans le syllabus)

  • Pour chaque frontiere entre 2 partitions : 2 valeurs (une de chaque cote)
  • Exemple : frontiere entre <18 et 18-65 a la valeur 18 : tester 17 et 18
  • Exemple : frontiere entre 18-65 et >65 a la valeur 65 : tester 65 et 66
  • Total : 2 frontieres x 2 valeurs = 4 valeurs limites

BVA 3 valeurs

  • Pour chaque frontiere : 3 valeurs (frontiere + 1 de chaque cote)
  • Exemple frontiere a 18 : tester 17, 18, 19
  • Exemple frontiere a 65 : tester 64, 65, 66
  • Total : 2 frontieres x 3 valeurs = 6 valeurs limites (en eliminant les doublons)
Couverture BVA = valeurs limites testees / total valeurs limites x 100%
Comment resoudre un exercice BVA en 3 etapes
  1. Identifier les frontieres entre partitions (la ou le comportement change)
  2. Pour BVA 2-valeurs : pour chaque frontiere, prendre la valeur juste en-dessous et juste au-dessus (ex: frontiere a 18 → tester 17 et 18)
  3. Pour BVA 3-valeurs : pour chaque frontiere, prendre la frontiere + 1 de chaque cote (ex: frontiere a 18 → tester 17, 18, 19)
Exemple BVA 2-val : Partitions <0, 0-2, >2. Frontieres a 0 et 2.
Frontiere 0 : tester -1 et 0. Frontiere 2 : tester 2 et 3.
Total : 4 valeurs limites = {-1, 0, 2, 3}. Si tu testes les 4 → 100% couverture BVA.
Piege : Ne confonds pas BVA 2-valeurs et 3-valeurs ! Le syllabus utilise 2-valeurs par defaut. Si la question dit "two-value BVA", c'est 2 valeurs par frontiere, pas 3.

Tables de decision

  • Conditions : les entrees/situations (lignes du haut)
  • Actions : les sorties/resultats attendus (lignes du bas)
  • Regles : chaque colonne = une combinaison unique de conditions avec ses actions
  • Nombre de regles theorique = 2^n (n = nombre de conditions booleennes)
Couverture table de decision = regles testees / total regles x 100%
Pour identifier quelle regle couvre un cas de test : verifier la combinaison de conditions et trouver la colonne correspondante.
Comment resoudre un exercice de table de decision
  1. Lire le cas de test : extraire les valeurs de chaque condition (ex: "19 ans, non inscrit, sans experience")
  2. Mapper chaque condition a la ligne correspondante de la table (Age=19-65, Inscrit=NON, Exp=0-4)
  3. Trouver la colonne ou TOUTES les conditions correspondent → c'est la regle couverte
  4. Pour la couverture : compter combien de colonnes/regles sont couvertes par l'ensemble des cas de test
Exemple : TC: homme de 66 ans, non inscrit. Dans la table : Age >65, Inscrit=NON. Chercher la colonne avec >65 et NON → c'est R4.

Transitions d'etat

  • Etat : situation dans laquelle le systeme se trouve
  • Transition : changement d'un etat a un autre
  • Evenement : ce qui declenche une transition
  • Action : ce qui resulte d'une transition
  • Garde : condition supplementaire pour qu'une transition ait lieu
Couverture transitions = transitions executees / total transitions valides x 100%
Comment resoudre un exercice de transitions d'etat
  1. Dessiner le graphe a partir de la table : etats = cercles, transitions = fleches avec evenements
  2. Lister toutes les transitions valides (compter les fleches distinctes)
  3. Tracer le chemin du cas de test en suivant les evenements un par un depuis l'etat initial
  4. Compter les transitions distinctes couvertes par le chemin
  5. Verifier la faisabilite : apres un etat final (End), plus aucune transition n'est possible !
Exemple : Sequence "Available, ChangeRoom, NotAvailable, Available, Pay"
S1→S2 (Available) → S2→S1 (ChangeRoom) → S1→S3 (NotAvailable) → S3→S2 (Available) → S2→S4 (Pay)
= 5 transitions distinctes couvertes sur 7 = 71% couverture.
Piege : Un meme evenement peut correspondre a des transitions DIFFERENTES selon l'etat de depart ! "Available" depuis S1 (→S2) n'est PAS la meme transition que "Available" depuis S3 (→S2).

Couverture des instructions

  • Chaque instruction du code executee au moins une fois
  • Mesure : instructions executees / total instructions x 100%
100% couverture instructions NE GARANTIT PAS 100% couverture branches ! Une branche "else" vide peut ne pas etre testee.

Couverture des branches

  • Chaque branche (vrai ET faux) de chaque decision executee au moins une fois
  • Mesure : branches executees / total branches x 100%
100% branches → 100% instructions (garanti) | 100% instructions ↗ 100% branches (PAS garanti)
Comment verifier la couverture d'instructions et de branches
  1. Tracer le chemin du cas de test dans le code (quelles lignes sont executees)
  2. Instructions : cocher chaque ligne executee. Couverture = lignes cochees / total lignes
  3. Branches : pour chaque IF/decision, verifier si le chemin VRAI et le chemin FAUX ont ete empruntes
  4. Rappel : 100% branches garantit 100% instructions. L'inverse est FAUX.
Piege : Un IF sans ELSE a quand meme 2 branches (vrai et faux). Si tu ne testes que le cas vrai, tu as 100% instructions mais seulement 50% branches.

Error guessing (Supposition d'erreurs)

  • Le testeur utilise son experience pour anticiper les erreurs, defauts et defaillances
  • Base sur : defauts passes, erreurs typiques des developpeurs, types de defaillances connues
  • Cree des "listes de bugs" ou "attaques" (taxonomies de defauts)
Error guessing n'anticipe PAS les causes racines ! Il anticipe les erreurs, defauts et defaillances.

Test exploratoire

  • Conception, execution et evaluation des tests simultanement
  • Utilise des chartes de test (session-based)
  • Peut utiliser des techniques boite noire pendant l'exploration
  • Ideal quand les specifications sont limitees ou le temps est court
Le test exploratoire ne permet PAS de predire de maniere fiable le nombre de defauts restants (pas de metriques de couverture formelles).

Test base sur des checklists

Le testeur utilise une liste de conditions a verifier. Les checklists sont construites a partir de l'experience, des standards, ou des defauts connus. La couverture peut etre imprecise car les items sont souvent a un niveau d'abstraction eleve.

User stories : Card, Conversation, Confirmation

  • Card : Support physique ou numerique decrivant la user story
  • Conversation : Echanges entre equipe pour clarifier les details
  • Confirmation : Criteres d'acceptation utilises pour confirmer que la story est complete

Collaboration pour comprendre ce qui doit etre livre : les user stories sont creees ENSEMBLE par representants metier, developpeurs et testeurs.

Criteres d'acceptation : INVEST et Given/When/Then

  • INVEST : Independent, Negotiable, Valuable, Estimable, Small, Testable
  • Given/When/Then : Given [contexte initial], When [action], Then [resultat attendu]

Chapitre 5 - Gestion des tests ▶

Plan de test : contenu

  • Contexte du test (portee, objectifs, contraintes)
  • Approche de test (niveaux, types, techniques, criteres, metriques)
  • Communication (qui recoit quels rapports, frequence)
  • Registre des risques
  • Calendrier, budget, ressources

Criteres d'entree vs Criteres de sortie

Criteres d'entree (avant de commencer)Criteres de sortie (pour terminer)
Disponibilite de l'environnement de testNiveau de couverture atteint (exigences, code)
Disponibilite des outils de testDensite de defauts estimee atteinte
Code testable disponibleNombre de defauts non corriges dans les limites
Donnees de test disponiblesTests de regression automatises passes

Techniques d'estimation

TechniqueDescription
Estimation basee sur les ratiosUtilise un ratio standard (ex: 1 jour de dev = 0.5 jour de test)
Estimation a 3 pointsFormule : E = (a + 4m + b) / 6 (a=optimiste, m=probable, b=pessimiste)
Planning poker (consensus)Chaque membre estime independamment, puis discussion jusqu'au consensus
E = (optimiste + 4 x plus probable + pessimiste) / 6
Comment calculer l'estimation 3 points
  1. Identifier les 3 valeurs : a (optimiste), m (plus probable), b (pessimiste)
  2. Appliquer la formule : E = (a + 4×m + b) / 6
  3. Multiplier par le nombre d'elements (cas de test, taches, etc.)
Exemple : Meilleur cas = 1h, probable = 3h, pire = 8h.
E = (1 + 4×3 + 8) / 6 = (1 + 12 + 8) / 6 = 21 / 6 = 3.5h par cas de test.
Pour 4 cas de test : 3.5 × 4 = 14 heures.
Piege : N'oublie pas de multiplier par le nombre d'elements ! L'erreur classique est de donner 3.5h (un seul cas) au lieu de 14h (les 4).

Priorisation des cas de test

  • Basee sur le risque : tester d'abord les cas a haut risque
  • Couverture additionnelle : choisir les cas qui augmentent le plus la couverture
  • Basee sur les exigences : prioriser selon l'importance des exigences

Pyramide de test

  • Base (beaucoup) : Tests unitaires / composants (rapides, peu couteux, automatises)
  • Milieu (moyen) : Tests d'integration (API, services)
  • Sommet (peu) : Tests UI / systeme / end-to-end (lents, couteux)

Plus on monte dans la pyramide, moins il y a de tests mais plus ils sont couteux et lents.

Gestion des risques

Risque = Probabilite x Impact
Comment calculer le risque
  1. Formule : Niveau de risque = Probabilite × Impact
  2. Si on te donne le niveau et la probabilite → Impact = Niveau / Probabilite
  3. Si on te donne le niveau et l'impact → Probabilite = Niveau / Impact
Exemple : Niveau = 1000$, Probabilite = 50% (= 0.5).
Impact = 1000 / 0.5 = 2000$.

Outils facilitant l'execution des tests

Les outils DevOps/CI-CD et les outils non-fonctionnels facilitent particulierement l'execution des tests en permettant l'automatisation de l'execution et du reporting.

Avantages de l'automatisation

  • Execution plus rapide des tests repetitifs
  • Plus grande couverture de test possible
  • Moins d'erreurs humaines dans l'execution
  • Metriques de couverture objectives et mesurables
  • Feedback plus rapide aux developpeurs
  • Reduction du temps d'execution des tests de regression

Risques de l'automatisation

  • Attentes irrealistes (l'automatisation ne remplace pas tout le test manuel)
  • Sous-estimation de l'effort de maintenance des scripts
  • Incompatibilite avec certaines plateformes ou technologies
  • Faux sentiment de securite (les tests automatises peuvent manquer des defauts)
  • Competences techniques requises pour l'equipe
  • Dependance a un outil specifique (vendor lock-in)

Mnemoniques et astuces d'examen

  • "PLUS probable", "NE PAS", "CORRECT" : attention aux mots-cles dans les questions d'examen. Lisez CHAQUE mot.
  • 100% branches implique 100% instructions (mais PAS l'inverse). C'est une question classique de l'examen.
  • Corriger n'est PAS un objectif du test. Le test detecte les defauts, le debogage les corrige.
  • Error guessing anticipe les erreurs, defauts et defaillances, mais PAS les causes racines.
  • "Pesticide paradox" / Usure des tests = memes tests repetes ne trouvent plus rien. Solution : varier les tests.
  • "Illusion d'absence de defauts" = 0 bug ne signifie pas que le logiciel satisfait les utilisateurs.
  • Confirmation = re-tester ce qui a echoue. Regression = re-tester ce qui marchait. Deux concepts DIFFERENTS !
  • Test de maintenance - 3 declencheurs : modification du systeme, changement d'environnement, retrait du systeme.
  • Revues : on trouve des DEFAUTS (pas des defaillances). Les defaillances n'apparaissent qu'a l'execution.
  • Walkthrough : dirige par l'AUTEUR. Inspection : dirige par un facilitateur FORME.
  • Processus de revue : 5 etapes exactement dans l'ordre. Planification AVANT initiation.
  • Test exploratoire : ne permet PAS de predire le nombre de defauts restants.
  • User stories : Card, Conversation, Confirmation. Creees ENSEMBLE par toute l'equipe.
  • INVEST : Independent, Negotiable, Valuable, Estimable, Small, Testable.
  • Shift-left : tester tot = reviser exigences, ecrire tests avant code, analyse statique avant dynamique.
